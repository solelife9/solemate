## 1. 러닝 기록 유실 — 경로 추적

### 1.1 러닝 중 앱 강제 종료 (L-1)

**두 겹으로 막혀 있다.**

```ts
// lib/runTracker.ts:34,38 — 스칼라와 경로를 분리해 쓰는 주기
const STATE_WRITE_MS = 3000;   // 거리·시간·일시정지·목표
const ROUTE_WRITE_MS = 15000;  // 경로(러닝이 길어질수록 커지는 유일한 필드)
```

분리가 옳다. 스칼라는 작고 자주 바뀌어 3초마다 써도 싸고, 경로는 길이에 비례해 커져
같이 쓰면 매번 전체를 다시 직렬화해야 한다. **그래서 강제 종료로 잃는 것은 최대 3초의
거리·시간이고, 경로 모양만 최대 15초 끊긴다** — 기록의 정확도(거리·시간)는 3초 상한이다.

다음 실행에서 복구 다이얼로그가 뜬다:

```ts
// App.tsx:730-760
const snap = await loadSnapshot();
if (asked || !isResumable(snap) || !snap) return;
// → '버리기' / '기록 저장' / '이어 달리기'
```

`isResumable` 은 거리·시간·경로 중 하나라도 있으면 true 라(`runPersistence.ts:156`),
**의미 있는 진행이 있었던 러닝은 반드시 사용자에게 물어본다.** 조용히 버리지 않는다.

**'이어 달리기' 는 실제로 이어진다** — GPS/센서를 다시 켜고 누적 거리·경과를 시드한다
(`App.tsx:751-756`, `resumeMode='continue'`). 그리고 재개 시 **앵커를 비운다**:

```ts
// lib/runTracker.ts:436
this.lastGood = null; // 공백 가로지르는 허위 거리 방지(재개 첫 fix = 새 앵커)
```

공백 동안 주자가 이동했을 수 있으므로 그 구간을 거리로 계상하지 않는다. **덜 세는 쪽으로
틀리게** 한 선택이고, 러닝 앱에서는 이게 옳다(없던 거리를 만들어내는 것이 더 나쁘다).

### 1.2 저장 실패 시 재시도와 사용자 인지 (L-6)

**두 층 모두 사용자에게 도달한다.**

| 층 | 임계 | 사용자에게 | 근거 |
|---|---|---|---|
| 러닝 중 스냅샷 | 연속 3회(≈9초) | 러닝 화면 '백업 안 됨' 줄 | `runTracker.ts:37` |
| 앱 전반 캐시 쓰기 | 연속 2회 | 토스트 「저장 공간이 부족해요 — 기록이 저장되지 않을 수 있어요」 | `storageAlert.ts:22,28` |

설계 원칙도 옳게 적혀 있다 — 한 번의 실패로 소리치지 않고(일시적일 수 있다), 쿨다운
10분으로 같은 말을 반복하지 않고, 성공하면 카운터를 되돌린다. **러닝 중에는 다이얼로그가
아니라 토스트/한 줄**로 흐름을 막지 않는다.

> **다만 클라우드 동기 실패는 이 대접을 못 받는다 — §3.1(D-1) 참조.**

### 1.3 완주 저장 순서 (L-3, L-4)

```ts
// App.tsx:963-976 (요약)
try { if(route) await setItem('route_'+localId, route); await setItem('time_'+localId, timeStr); }
catch(e){ routeSidecarOk=false; recordError(e,'storage: run sidecar write'); }
await persistRunToCache(record,{keepRoute:!!route&&!routeSidecarOk});
setRuns(prev=>[record,...prev]);
```

순서가 **영속 → 상태 반영**이다. 그래서 `setRuns` 직후 앱이 죽어도 캐시에 이미 durable 하게
들어가 있다. 그리고 사이드키 실패를 **삼키지 않고 관측해**, 실패했을 때만 캐시에 경로를
남긴다(`keepRoute`). 캐시는 평소 경로를 빼고 저장하므로(F-08), 이 분기가 없으면 사이드키가
실패한 순간 **경로의 로컬 사본이 하나도 안 남는다.** 이 한 줄이 그걸 막는다.

### 1.4 러닝 중 네트워크 단절 (L-5)

**러닝 경로에 네트워크 호출이 없다.** GPS·센서·로컬 저장뿐이다. 저장 후의 동기는
`runCloudSync` 가 별도로, 비차단으로 한다. 즉 **비행기 모드로 풀코스를 달려도 기록은 온전**하고,
연결이 돌아오면 다음 동기 트리거(앱 이탈·복귀·데이터 변경)에서 올라간다.

Firestore 네이티브 SDK 의 오프라인 영속이 그 사이의 쓰기를 큐잉한다 — **다만 이걸 코드에서
명시적으로 켜지 않는다**(D-6). 기본값이 ON 이라 지금 동작하지만, 기본값에 기대는 것이라
버전이 바뀌면 조용히 달라질 수 있다.

## 2. 동기화

### 2.1 여러 기기 동시 쓰기 (L-7) — **막혀 있다**

```ts
// lib/firebaseCloudPort.ts:309-320
return await runTransaction(getFirestore(), async tx => {
  const snapshot = await tx.get(ref);          // 트랜잭션 안에서 원격을 다시 읽는다
  const merged = merge(local, remote);          // 무손실 union
  ...
  tx.set(ref, nextDoc);
});
```

`pull → merge → push` 를 한 트랜잭션에 묶어 **경합 창을 닫았다.** 다른 기기가 그 사이 쓴
값이 `tx.get` 으로 보이고, Firestore 가 경합을 감지하면 트랜잭션을 자동 재시도한다.
머지는 id 합집합이라 어느 쪽 레코드도 버리지 않는다(`cloudSync.ts:210-249`).

동기 왕복(await) 중에 추가/편집한 런도 보존된다:

```ts
// App.tsx:1161 — 전체 교체가 아니라 함수형 갱신
setRuns(preserve ? prev => reconcileLivePreservingLocal(prev, rPart.live, tomb) : rPart.live);
```

선행 감사 HIGH #2(동기 왕복 중 추가한 런이 머지 덮어쓰기로 유실)가 **여기서 고쳐졌다.**

### 2.2 tombstone(soft-delete) — **Firestore 에서도 동작한다**

묘비는 페이로드 본문에 실려 올라간다:

```ts
// App.tsx:1125-1127
shoes:[...shoes,...tombstones.shoes],
runs:[...runs,...tombstones.runs],
```

머지에서 묘비가 이기는 규칙도 성립한다 — `markDeleted` 가 `deleted:true` + 갱신된
`updatedAt` 을 박으므로 '최신 우선' 규칙만으로 (한 기기서 지운) 묘비가 (다른 기기의 더
오래된) live 레코드를 이긴다. 동률(같은 ms)일 때만 추가로 묘비를 우선해 경계 케이스도 막는다
(`cloudSync.ts:236-239`).

부팅 부활도 막혀 있다 — `initUser` 가 `tombstones_v1` 로 부팅 라이브를 한 번 거른다
(`App.tsx:824-836`). 선행 감사 #4·#5 가 여기서 고쳐졌다.

> **그런데 묘비를 아무도 정리하지 않는다 → §3.1 (D-1).**

### 2.3 `updatedAt` 기반 최신 우선 — **실효하지만 기준이 흔들린다**

머지 규칙 자체는 옳다(§2.2). 문제는 **그 숫자를 누가 찍느냐**다 → §3.2 (D-2).

### 2.4 오프라인 기록의 합류 (L-8) — **막혀 있다**

세 겹이다.
1. **로컬 정본** — 부팅 캐시가 신발·런의 로컬 진실이고, 러닝 저장이 여기에 직접 쓴다.
2. **무손실 union** — 합류 시 remote 에만 있는 것도, local 에만 있는 것도 버리지 않는다.
3. **Firestore 오프라인 영속** — 연결 복구 시 큐잉된 쓰기가 서버로 간다.

레거시 pending 큐(`pending_runs`)는 **REST 시절 유물**이고 지금은 넣는 쪽 호출부가 0 이다
(`runPersistence.ts:10-16`). 부팅 때 읽어서 오버레이하는 이유는 **구 버전에서 올라온 기기의
큐를 비워 주기 위해서**다. 새 설치는 항상 빈 큐 → 부팅마다 빈 읽기 1회(D-7, 무해).

## 3. 새 구조에서 생긴 위험

### 3.1 🟠 `MAJOR` D-1 — 묘비가 영원히 쌓이고, 동기가 멎어도 사용자는 모른다

**묘비를 정리하는 코드가 없다.** `lib/cloudSync.ts` 전체에 prune·expire·maxAge 가 하나도
없고, 묘비는 `backupData` 본문에 그대로 실려 매 동기마다 다시 올라간다.

즉 **삭제할 때마다 백업 문서가 커지고, 절대 작아지지 않는다.** 신발 하나, 런 하나를 지울
때마다 그 레코드 전체(런이면 필드 15개 + 메모)가 묘비로 영구 보존된다.

Firestore 문서 상한은 **1MiB** 다. 이 프로젝트는 이미 한 번 그 벽에 부딪혔다 —
`8f4ef86`("백업 문서 1MiB 폭탄 — GPS 경로를 사이드카로 분리"). 그때는 경로가 범인이었고
사이드카 분리로 해결했다. **묘비는 같은 성질의 두 번째 폭탄이고, 아직 안 터졌을 뿐이다.**

`[추정]` 런 묘비 하나를 ~300B 로 보면 1MiB 는 약 3,500건이다. 일반 사용자가 도달하기는
어렵지만 **테스트를 많이 한 계정·기록을 정리하는 습관이 있는 사용자**는 도달한다.

**진짜 문제는 그 다음이다 — 터져도 조용하다.**

```ts
// App.tsx:1338
}catch(e){reportIssue('cloud sync',e);}
```

동기 실패는 Crashlytics 로만 간다. **사용자에게는 아무 말도 하지 않는다.** 캐시 쓰기 실패는
토스트로 알리면서(§1.2), 정작 "클라우드에 백업이 안 되고 있다"는 침묵이다. 화면의
`lastSyncAt` 칩이 낡아 가는 것이 유일한 단서인데, 그걸 눈치채라고 요구할 수는 없다.

**결과:** 백업이 멈춘 채로 몇 주가 지나고, 기기를 바꾸거나 앱을 지웠을 때 **그 사이의 모든
기록이 없다는 걸 그때 처음 안다.**

**선택지 — `[승인 필요]`**
1. **묘비에 유효기간을 둔다(권장).** 삭제가 모든 기기에 전파되고 나면 묘비는 역할이 끝난다.
   90일이면 충분히 안전하다(그 안에 안 켠 기기는 어차피 전량 복원 대상이다).
   `mergeCloudData` 에서 오래된 묘비를 떨어뜨리면 문서가 스스로 줄어든다.
2. **묘비를 id 만 남기고 껍데기로 줄인다.** 머지에 필요한 건 `id`·`deleted`·`updatedAt`
   뿐이다. 나머지 필드는 지금 아무도 안 읽는다. 크기가 한 자릿수 배 줄어든다.
3. **동기 실패를 사용자에게 알린다(1과 무관하게 필요).** 캐시 실패와 같은 규약 —
   연속 N회 실패 시 토스트, 쿨다운 적용.

> **1+2+3 을 함께 하는 것이 맞다.** 1·2 는 벽을 미루고, 3 은 벽에 부딪혔을 때 알게 한다.

### 3.2 🟠 `MAJOR` D-2 — 최신 우선의 기준이 클라이언트 시계다

```ts
// lib/cloudSync.ts:59-64
export function stampUpdatedAt<T extends object>(record: T, now: number = Date.now()) {
  return { ...record, updatedAt: now };
}
```

`Date.now()` 는 **그 기기의 시계**다. 서버 시각이 아니다.

두 기기의 시계가 어긋나면(자동 설정을 꺼둔 기기, 시간대 이동 직후, 배터리 방전 후 부팅)
**시계가 빠른 기기가 항상 이긴다.** 폰의 시계가 10분 빠르면, 워치나 다른 폰에서 방금 한
편집은 10분 전 것으로 보여 **더 오래된 값에 밀려 사라진다.**

이건 이론적 우려가 아니다 — 이 앱은 **폰과 애플워치가 같은 기록을 쓴다.** 두 기기의 시계가
정확히 같을 이유가 없다.

같은 결함이 설정에도 있다(`settings_updated_at` 도 클라이언트 시각). 그래서 **다른 기기에서
바꾼 단위·목표·체중이 조용히 되돌아갈 수 있다.**

**선택지 — `[승인 필요]`**
1. **`serverTimestamp()` 로 찍는다(정석).** 다만 현재 구조는 레코드가 **문서 본문의 배열
   원소**라, Firestore 의 `serverTimestamp()` 를 배열 원소에 넣을 수 없다. 레코드를
   하위 문서로 쪼개야 해서 **저장 구조 변경**이다(큰 작업).
2. **쓰기 시각을 서버 시각으로 보정한다(현실적).** 동기할 때 서버 문서에 `serverTimestamp`
   필드를 하나 두고, 응답으로 받은 서버 시각과 기기 시각의 차(offset)를 저장한다.
   이후 `stampUpdatedAt` 이 `Date.now() + offset` 을 쓴다. **구조 변경 없이 시계 어긋남을
   대부분 흡수**한다.
3. **아무것도 안 한다.** 단일 기기 사용자에게는 문제가 없다. 다만 워치를 쓰는 순간 노출된다.

> **2 를 권한다.** 저장 구조를 안 건드리고 실효가 크다. 1 은 리더보드 재설계처럼 구조를
> 손볼 때 함께 가는 것이 맞다.

### 3.3 🟠 `MAJOR` D-3 — 런을 지워도 클라우드의 경로가 남는다

`deleteRun` 은 로컬을 꼼꼼히 지운다 — `route_`·`time_`·`surface_`·`splits_`·`paceTrack_`·
`hrTrack_`·`gapTrack_`·`runphoto_` 전부(`App.tsx:1049-1058` 구간). **그런데 클라우드 사이드카
`userBackups/{uid}/runDetails/{runId}` 는 건드리지 않는다.**

확인: **`deleteRunDetail` 이라는 API 자체가 존재하지 않는다.** `runDetailRef` 를 쓰는 곳은
push·pull·탈퇴 순회 삭제 세 군데뿐이다(`firebaseCloudPort.ts:203,251,304,309`).

즉 **탈퇴하지 않는 한, 삭제한 런의 GPS 경로·심박·스플릿이 서버에 영구히 남는다.**

두 가지가 걸린다.
- **사용자 기대와 다르다.** 기록을 지웠는데 이동 경로가 서버에 남아 있다.
- **처리방침과 어긋난다.** 01 감사에서 `search_misses` 로 같은 종류의 문제를 이미 지적했다
  (탈퇴해도 남는 데이터). 이건 **탈퇴가 아니라 개별 삭제**여서 더 직접적이다.

**조치 — `[승인 필요]` (작다):** `CloudPort` 에 `deleteRunDetail(runId)` 를 추가하고
`deleteRun` 에서 부른다. 규칙은 이미 본인 문서 삭제를 허용한다(`userBackups/{uid}/{**}`).
실패해도 삭제 흐름을 막지 않되(비차단), **다음 동기에서 재시도할 수 있게 표시를 남긴다** —
안 그러면 오프라인에서 지운 런의 상세가 영영 안 지워진다.

### 3.4 🟡 `MINOR` D-5 — 삭제한 런의 동기 마커가 남는다

`detail_pushed_<id>` 와 `detail_absent_<id>`(2026-08-01 추가)는 `deleteRun` 의 정리 목록에
없다. 런 하나당 최대 2개의 키가 영구히 남는다. 기능 영향은 없고(그 런은 더 이상 순회되지
않는다) 저장소 누수만 있다. D-3 을 고칠 때 같이 지우면 된다.

## 4. 신발 마일리지

### 4.1 어디에 저장되고 어떻게 계산되는가 — **저장되지 않는다. 매번 계산한다**

```ts
// lib/shoe.ts:117-135
const startKm = Number(shoe?.start_km ?? 0) || 0;
const ranKm = runs.reduce((sum, r) => r.shoe_id === shoe.id ? sum + km : sum, 0);
const clientKm = startKm + ranKm;
const serverTotal = Number(shoe?.total_km);
const usedKm = Number.isFinite(serverTotal) && serverTotal >= 0
  ? Math.max(serverTotal, clientKm) : clientKm;
```

**누적 거리는 저장된 값이 아니라 파생값이다** — 등록 시 입력한 `start_km` 에 그 신발로 달린
런의 km 를 매번 더한다. 이 설계 자체는 옳다(단일 진실 = 런 목록, 이중 기록의 불일치 없음).

`total_km` 은 **REST 서버가 유지하던 필드**다. 코드가 이 값을 **읽기는 하지만 쓰지는 않는다** —
저장소 전체에서 `total_km` 에 값을 넣는 곳은 devSeed(개발용 목)와 HomeScreen 의 표시용 주입뿐이고,
**Firestore 로 이관된 뒤로는 아무도 갱신하지 않는다.**

> 즉 **지금 `usedKm` 은 사실상 100% 파생값**이고, `Math.max(serverTotal, clientKm)` 의 서버
> 항은 옛 데이터가 남은 계정에서만 의미를 갖는다. 코드 주석("서버 truth 를 우선")은 **현재
> 구조와 어긋난다** — 서버 truth 는 더 이상 갱신되지 않는다.

### 4.2 🟠 `MAJOR` D-4 — 런이 사라지면 마일리지가 말없이 줄어든다

파생값이라는 성질의 뒷면이다. **런 목록이 곧 마일리지이므로, 런이 줄면 마일리지가 준다.**

- 의도한 삭제라면 옳은 동작이다(사용자가 지웠으니 줄어야 한다).
- **의도하지 않은 유실이라면 조용한 퇴행이다.** 신발 수명 링이 뒤로 감기고, 교체 알림이
  늦춰지고, 사용자는 **줄었다는 사실조차 모른다.**

무엇이 마일리지를 되돌릴 수 있나 — **아무것도 없다.** 독립 기록이 없어서 "원래 얼마였는지"를
아는 주체가 없다. 사용자가 기억해서 `start_km` 을 손으로 올리는 것이 유일한 복구다.

**이 앱의 차별점이 러닝화 내구도 관리라는 걸 생각하면** 이 지표만 유독 방어가 없는 셈이다.
런 한 건은 캐시·사이드카·묘비·클라우드로 네 겹으로 지키면서, **그 합계는 아무 데도 안 적어둔다.**

**선택지 — `[승인 필요]`**
1. **최고수위 표시(권장, 작다).** 신발 레코드에 `usedKmHighWater` 를 두고 파생값이 그보다
   커질 때만 갱신한다. 파생값이 그보다 **작아지면 그 차이를 사용자에게 알린다** —
   "이 신발의 기록 12km 가 보이지 않아요. 확인해 주세요." 되돌리지는 않되(삭제는 정당할 수
   있다) **조용하지 않게** 만든다.
2. **삭제 시에만 수위를 낮춘다.** `deleteRun` 이 명시적으로 수위를 재계산하면, 그 외의
   감소는 전부 '설명되지 않는 감소'로 확정된다. 1 보다 정확하지만 삭제 경로를 손봐야 한다.
3. **아무것도 안 한다.** 유실 자체가 드물다면 수용 가능하다. 다만 **드물다는 근거는 없다** —
   지금까지 마일리지 감소를 관측한 적이 없을 뿐이다(관측 수단이 없으므로).

> **1 을 권한다.** 필드 하나와 비교 한 줄이면 되고, "조용한 퇴행"을 "보이는 신호"로 바꾼다.

### 4.3 신발 삭제·은퇴 시 연결된 런 — **삭제해도 런은 남는다(옳다)**

| 동작 | 신발 | 그 신발의 런 | 마일리지 |
|---|---|---|---|
| **은퇴(retire)** | 숨김(`retired:true`) — 피커에서 빠짐 | **전부 보존** | 계속 계산됨(명예의 전당) |
| **삭제(delete)** | 묘비 → 목록에서 제거 | **전부 보존**(고아가 됨) | 신발이 없으니 집계 대상 없음 |

삭제 확인 문구도 정직하다 — 「신발 삭제 · **러닝 기록은 그대로 남아요.**」(`ShoesScreen.rn.tsx:194`).
런을 함께 지우지 않는 선택이 옳다. 런은 그 사람의 활동 기록이지 신발의 부속물이 아니다.

**다만 고아 런의 뒷정리는 없다.** 삭제된 신발을 참조하는 런이 기록 탭에 남는데, 그 런의
신발 이름을 어떻게 표시하는지는 화면 구현에 달렸다. `[민우 확인]` — **실기기에서 신발 하나를
지운 뒤 기록 탭에서 그 신발의 런이 어떻게 보이는지** 확인이 필요하다(빈칸/undefined 로 뜨면
버그, "삭제된 신발" 같은 문구면 정상).

### 8.1 각 조치에서 지킨 선

**D-1 의 유효기간에는 대가가 있다.** 90일 넘게 안 켠 기기는 그 사이 삭제된 레코드를 되살릴
수 있다(삭제 사실을 못 들었고 묘비도 이미 사라졌다). 그 확률보다 **문서가 터져 모든 기기의
동기가 멎는 쪽**이 훨씬 흔하고 나쁘다고 판단했다. 그리고 **시각을 모르는 묘비는 남긴다** —
언제 지웠는지 모르는데 떨어뜨리면 삭제가 취소된다.

**신발 묘비의 `name` 은 남겼다.** 껍데기화가 이걸 버리면 **지난 기록의 신발 이름이 빈칸**이
된다(`lib/appViewModel.buildNameById` 가 실제로 읽는다). 크기 절감보다 기록 온전함이 우선이다.

**D-2 의 offset 에는 상한(±24시간)을 뒀다.** 시계가 하루 넘게 틀린 기기보다, 잘못 계산된
offset 이 **모든 기록의 시각을 오염시켜 병합을 통째로 뒤집는 쪽**이 훨씬 위험하다.
채택 못 하면 보정하지 않는다(offset 0 = 예전과 동일 동작).

**D-3 은 큐가 핵심이다.** Firestore 오프라인 영속이 대부분의 삭제를 큐잉해 주지만,
**로그인 전이거나 포트가 삭제를 지원하지 않으면** 호출 자체가 실패한다. 표시를 안 남기면
그 런의 경로는 서버에 영영 남는다 — 사용자는 지웠다고 믿는데.

**D-4 는 되돌리지 않는다.** 앱은 무엇이 옳은지 모른다(삭제가 정당했을 수도 있다).
목적은 **조용하지 않게 만드는 것**이다 — 한 번 알린 뒤 그 값으로 다시 기준을 잡아
같은 일로 계속 나무라지 않는다. 삭제처럼 정당한 감소는 `deleteRun` 이 수위를 미리 내려
애초에 걸리지 않는다. 그리고 **수위가 없으면 판정하지 않는다** — 기준이 없는데 경고하면
기존 사용자 전원에게 오탐이 뜬다.

### 8.2 D-2 가 완전한 해결은 아니다

offset 은 **이 기기가 한 번이라도 동기해 본 뒤에** 생긴다. 첫 동기 전에 만든 레코드는
보정되지 않은 시각으로 스탬프된다. 완전한 해결은 레코드를 하위 문서로 쪼개 서버
타임스탬프를 직접 쓰는 것인데, 그건 저장 구조 변경이라 리더보드 재설계처럼 큰 작업과
함께 가야 한다. **지금 구조에서 할 수 있는 최선**이고, 흔한 경우(오래 쓴 두 기기)는 덮는다.
