## 2. 공격 시나리오 8종 — 실행 결과

`tests/rules/attack.rules.test.ts` · **35건 전부 방어 성공**.

### 1. 다른 유저의 러닝 기록을 읽을 수 있는가 → **불가능** (근거 L56, L59)
백업 본체·런 상세 사이드카·컬렉션 전체 조회·하위 컬렉션 목록 — 4가지 경로 전부 `PERMISSION_DENIED`.

### 2. 다른 유저의 신발/기록을 수정·삭제할 수 있는가 → **불가능** (L56, L59)
덮어쓰기·부분수정(`updateDoc`)·삭제·사이드카 삭제 전부 차단.

### 3. 일반 유저가 신발 카탈로그를 수정할 수 있는가 → **불가능** (L106, L97)
생성·변조·삭제 전부 차단. `races` 도 동일.

### 4. 인증 없이 읽히는 컬렉션이 있는가 → **없음** (L96, L105, L56, L77, L117)
비로그인으로 `shoes`·`races`·`userBackups`·`leaderboards` 읽기, 신호 생성 전부 차단.
> 단, `signedIn()` 은 **익명 계정도 통과**한다. 현재 익명 로그인은 UI 에 없지만
> (`LoginScreen` 미노출), 구현은 살아 있다(`firebaseCloudPort.ts:190`). 익명을 켜는 순간
> `races`·`shoes` 카탈로그는 **익명 계정에게도 열린다** — 큐레이션 데이터라 피해는 작지만
> 인지하고 켜야 한다.

### 5. 남의 uid 로 문서를 생성할 수 있는가 → **불가능** (L56, L79, L33)
남의 경로에 생성·남의 uid 필드 심기 전부 차단. 본인 uid 로는 정상 생성(대조군 통과).

### 6. 임의 필드 추가·타입 변조 → **부분 가능** ⚠️ `MAJOR`

| 대상 | 결과 | 근거 |

| `search_misses` 모르는 필드 | 차단 | L118 `hasOnly()` |
| `shoe_requests` 모르는 `source` | 차단 | L133-134 enum |
| **`userBackups` 내 문서에 임의 형태** | **통과** ⚠️ | L56 에 형태 검증 없음 |

**해석:** 둘 다 *자기 문서*에만 가능하므로 **타인 피해는 없다.** 다만
(a) 랭킹 엔트리에 임의 데이터를 실어 컬렉션을 오염시킬 수 있고 — 리더보드는 현재 꺼져

(b) `userBackups` 는 형태 자유가 **설계 의도**다(백업 페이로드 스키마가 계속 변한다).

## 3. 🔴 `BLOCKER` S-1 — 계정 전환 시 데이터 격리 실패

**규칙 감사만으로는 안 잡히는 결함이다.** 두 사용자가 각자 '자기 문서'에 쓰는 것이라
Firestore 입장에서는 완벽히 합법이다. 깨지는 곳은 **앱의 상태 관리**다.

### 재현 경로 (앱 재시작조차 필요 없다)

```
1. A 로그인 → 사용 → 로컬 캐시(cache_shoes_v1/cache_runs_v1)에 A 의 기록
2. A 로그아웃  ← ProfileScreen.rn.tsx:342-355 doSignOut
                 세션·화면만 정리한다. shoes/runs 상태도, 로컬 캐시도 비우지 않는다.
                 (탈퇴 경로 App.tsx:1292 만 AsyncStorage.clear() 를 한다)
3. B 로그인   → authUser 갱신. 그런데 initUser 는 App.tsx:392 에서 useEffect(...,[]) 로
                 **마운트 때 한 번만** 돌므로 다시 읽지 않는다 → 메모리엔 A 의 기록 그대로
4. runCloudSync 발동 → backupData(= A 의 신발·런)를 B 의 uid 문서에 syncMerge
   → **A 의 기록이 B 계정 클라우드에 영구 병합된다**
```

### 피해
- B 가 A 의 러닝 기록·신발·경로(GPS 이동 이력)를 본다 — **위치정보 유출**
- A 의 기록이 B 계정에 섞여 **양쪽 데이터가 오염**된다
- 클라우드에 올라간 뒤엔 어느 것이 누구 것인지 구분할 근거가 없다

### 근본 원인
로컬 캐시에 **소유자 표시가 없다.** `lib/bootCache.ts`·`lib/runCache.ts` 어디에도 uid 개념이
없고, 캐시 키도 계정별로 나뉘어 있지 않다(`cache_shoes_v1` 단일 슬롯).

### 조치 (이번 감사에서 적용)
`lib/cacheOwner.ts` 신설 — 캐시에 소유자 uid 를 기록하고, **동기 직전에 주인을 확인해
다르면 동기를 통째로 건너뛴다**(`App.tsx` runCloudSync). 성공한 동기 후 주인을 등록한다.

**의도적으로 '삭제'가 아니라 '차단'으로 했다.** 로그아웃 시 캐시를 비우는 쪽이 간단하지만,
오프라인에서 쌓아둔 미동기 기록이 로그아웃 한 번에 사라진다(Iron Law: 사용자 데이터 파괴 금지).

### 남은 것 — `[승인 필요]`
차단만으로는 **B 가 화면에서 A 의 기록을 보는 것**까지는 막지 못한다(클라우드 오염은 막힌다).
완전한 해결은 **계정별 캐시 격리**(`cache_runs_v1__<uid>` 네임스페이스 + 경로 사이드카·
펜딩 큐·묘비까지 동일 적용)인데, 저장소 구조를 바꾸는 작업이라 데이터 안전 검토가 필요하다.
→ 민우님 승인 후 진행.

## 5. 인증

### 5.1 소셜 로그인 흐름 — **audience 검증이 제대로 있다** ✅

가장 흔한 취약점은 "클라이언트가 준 토큰을 그대로 믿는 것"이다. 그러면 **공격자가 자기
앱에서 발급한 카카오 토큰으로 우리 앱 계정을 만들 수 있다.** 이 앱은 막혀 있다:

- **카카오**(`functions/index.js:84-38`): `access_token_info` 로 조회한 뒤
  **`info.app_id === KAKAO_APP_ID` 를 대조**한다. 다르면 401.
  환경변수 미설정이면 **503 으로 로그인을 거부**한다(fail-closed) — 검증 불가 상태에서
  통과시키지 않는다. 설계가 옳다.
- **네이버**(`functions/index.js:123-124`, `functions/naverAuth.js`): 네이버는
  introspection 이 없어, **우리 앱의 client_id/secret 으로 refresh token 을 교환**해
  audience 를 증명한다. 남의 앱 토큰이면 교환이 실패한다. 우회 설계로 타당하다.
- 커스텀 토큰은 **Cloud Functions(서버)** 에서만 발급된다. 클라이언트가 uid 를 정하지 못한다.

**실측 확인:** 배포된 함수에 일부러 잘못된 토큰을 보내니 **401**(503 아님) — 환경변수가
주입돼 있고 검증 경로가 살아 있다는 뜻이다.

### 5.2 익명 → 정식 계정 승격 시 데이터 유실 — `INFO`

현재 **익명 로그인은 UI 에 없다**(2026-07-30 소셜 전용 확정). 따라서 지금은 해당 없음.

다만 되살릴 경우를 위해 기록한다: 승격 경로가 **`linkWithCredential` 이 아니다.**
익명으로 쓰다 소셜로 로그인하면 **새 uid 가 발급**되고, 데이터는
`cloudSync.migrateDeviceToAccount` 로 옮기는 설계인데 — **그 함수는 프로덕션에서
호출되는 곳이 없다**(정의와 테스트만 존재). 즉 지금 상태로 익명을 켜면 승격 시
클라우드 데이터가 새 계정으로 따라가지 않는다. 익명 재도입 시 `linkWithCredential`
채택이 정석이다(uid 유지 → 친구·랭킹 이력 보존).

### 5.3 로그아웃 시 로컬 캐시 — **남는다** → §3 S-1 의 원인

`doSignOut`(`ProfileScreen.rn.tsx:342-355`)은 `cloudPort.signOut()` 후
`cloudUser`/`provider`/`lastSyncAt` 만 비운다. **신발·런 상태도 AsyncStorage 캐시도
그대로 남는다.** 다이얼로그도 "기록은 이 기기와 클라우드에 안전하게 남아요"라고
**의도적으로** 안내한다 — 단일 사용자 기기에서는 올바른 설계다(오프라인 데이터 보호).
문제는 그 전제가 깨지는 **공유 기기**다. §3 조치 참조.

### 5.4 계정 삭제가 Firestore 데이터를 전부 지우는가 — **거의. 두 곳이 남는다** `MAJOR`

`lib/firebaseCloudPort.ts` `deleteAccount()` 가 지우는 것:

| 대상 | 삭제 | 근거 |
|---|---|---|
| `userBackups/{uid}/runDetails/*` | ✅ 순회 삭제 | 하위 컬렉션은 부모 삭제로 안 지워진다는 걸 알고 처리 |
| `userBackups/{uid}` | ✅ | |
| `leaderboards/*/entries/{uid}` | ✅ 최근 24개월 순회 | 2026-07-30 추가 |
| Firebase Auth 계정 | ✅ `deleteUser` | `requires-recent-login` 은 한국어 안내로 전파 |
| 로컬 전체 | ✅ `AsyncStorage.clear()` (App.tsx:1292) | |
| **`search_misses/*`** | ❌ **남는다** | 문서에 `userId` 가 들어 있다 |
| **`shoe_requests/*`** | ❌ **남는다** | 〃 |

**두 컬렉션은 규칙상 클라이언트가 삭제할 수 없고**(L116, L124 `delete: if false`),
읽기도 막혀 있어 **자기 문서를 찾을 방법조차 없다.** 즉 탈퇴해도 "이 사람이 무엇을
검색했는지"가 `userId` 와 함께 서버에 남는다.

처리방침(§3)은 「계정 정보 — 회원 탈퇴 시까지」라고 적고 있어 **문서와 실제가 어긋난다.**
(2026-07-30 리더보드에서 고친 것과 **같은 종류의 문제가 한 번 더 있는 것**이다.)

**선택지 — `[승인 필요]`**
1. **`userId` 를 아예 저장하지 않는다**(권장). 신호의 목적(무엇이 없었나)에 uid 는 불필요하다.
   지우고 나면 파기 대상 자체가 사라지고 처리방침도 단순해진다.
2. 관리 스크립트로 탈퇴 uid 의 신호를 주기 삭제(운영 부담 + 탈퇴 시점 즉시성 없음).
3. 규칙을 열어 본인이 지우게 한다 — 읽기가 막혀 있어 찾을 수 없으므로 **불가**.
