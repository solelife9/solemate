# [3] 출시까지 남은 작업량

```
순수 손작업          25.7h  ÷ 3h/일  =  8.6일  →  9일
실기기 QA 에서 나올 수정 여유(+6h)              →  +2일
─────────────────────────────────────────────────
현실적 예상                                     11일
```

**그런데 11일이 출시일이 아니다.** 벽시계 시간은 아래 대기가 정한다 —

| 대기 | 길이 | 언제 시작되나 |
|---|---|---|
| **방통위 위치기반서비스 신고** | **수 주** | B-1 접수 즉시 (← **오늘 안 넣으면 그만큼 밀린다**) |
| Analytics 첫 수집 | 최대 24h | B-9 이후 |
| 단계 0 관찰 | 3일 | 심사 통과 후 |
| App Store 심사 | 24~48h(반려 시 더) | B-12 제출 후 |

> **결론:** 손으로 하는 일은 **11일이면 끝난다.** 출시일은 **방통위 접수일 + 3~6주** 근처에서 정해지고,
> 그 안에 11일은 통째로 들어간다. **그래서 순서 1번이 신고 접수다 — 중요해서가 아니라 남이 처리하는 시간이 제일 길어서다.**

**시간 산정에서 정직하게 밝힐 것**

- B-7 의 8시간 중 **5시간 러닝(§2 #12)은 실제로 달릴 필요가 없다.** 앱을 켠 채 5시간 두면(걷기·자전거·가방) 경로점 1.8만 개 규모와 스냅샷 쓰기 지연은 그대로 재현된다. 손이 묶이는 시간은 30분 남짓이다.
- B-7 의 잠금 30분·백그라운드 복귀는 **한 번의 러닝에 묶어서** 할 수 있다(달리는 중간에 잠갔다 풀고, 카톡 열었다 돌아오면 된다). 8시간은 그렇게 묶었을 때의 값이다.
- 실기기 QA 에서 버그가 **하나도 안 나올 확률은 낮다.** 그래서 +2일을 미리 잡았다.

# [4] 권장 작업 순서

> 원칙 세 가지. ① **대기가 긴 것부터 건다**(내 시간이 아니라 남의 시간이므로). ② **되돌릴 수 없는 것은 사용자 0명일 때**. ③ **화면이 확정된 뒤에 스크린샷을 찍는다.**

### 1일차 — 남이 처리할 일을 먼저 걸어둔다 (3h)

1. **B-1 방통위 신고 접수** (2h) — 기술자료는 `docs/legal/location-data-flow.md` 를 그대로 첨부. *이걸 넣는 순간부터 시계가 돌기 시작한다.*
2. **B-5 서비스 계정 키 폐기** (0.2h) — 지금 30초면 되고, 유출되면 규칙이 통째로 무의미해진다.
3. **B-13 필수 업데이트 화면 승인** (0.5h) — 대기 중 짬으로.

### 2일차 — 사용자 0명일 때만 안전한 것 (3h)

4. **B-4 콘솔 3종** (1h) — **App Check enforce 는 지금 켜야 한다.** 사용자가 생긴 뒤에 켜면 아직 업데이트 안 한 사람이 잠긴다. Maps 키 제한은 **`com.keego.app`** 로(TODO 의 `com.solemate` 는 낡았다).
5. **B-2 미커밋 10파일 정리** (0.5h) — 무엇이 빌드에 들어갔는지 나중에 되짚을 수 있어야 한다.
6. **B-3 CI 초록 1회** 착수 (1.5h) — 돌려놓고 다음으로 넘어간다.

### 3일차 — 빌드를 손에 넣는다 (3h)

7. **B-3 마무리** — 초록을 **눈으로 본 뒤에** 다음으로.
8. **B-6 빌드 23 → TestFlight → 폰 설치** (1.5h)
9. **B-10 게이트 리허설** (1.5h) — `config/app` 생성 → `--min` 을 현재 버전과 같게 → **안 뜨는 것 확인** → `--off`. *비상 장치를 비상 때 처음 써보면 안 된다.*

### 4~7일차 — 실기기 (12h, 이 구간이 제일 무겁다)

10. **B-7 실기기 QA 8건** + **B-8 최근 수정분 4건** — 러닝 3회에 묶는다.
    · 1회차(30분+): 잠금 → 해제 → 백그라운드 → 복귀 → 비행기모드 on/off → 강제 종료 → 이어 달리기
    · 2회차(짧게): 위치 권한 끈 채 시작·종료 / 권한 회수 → 재허용 / 비행기모드 완주 저장
    · 3회차(방치 5h): 경로점 규모·스냅샷 지연·배터리
    · 앉아서: 최대 글꼴 3곳 · 신규 설치 첫 로그인 · 비행기모드 탈퇴 · 신발 삭제 후 기록 탭 표시
11. **B-9 관측성 도착 확인** (2h) — 여기서 **일부러 크래시를 한 번 낸다.** Analytics 는 24h 뒤 재확인이므로 이 시점에 걸어둔다.
12. *나온 버그 수정 → CI 재확인 → 필요 시 빌드 24* (여유 2일)

### 8~9일차 — 제출물 (4h)

13. **B-11 스크린샷 재검증** (2h) — *반드시 10~12 이후.* QA 에서 수정이 나오면 화면이 바뀐다.
14. **B-12 ASC 폼 입력 + 제출** (2h) — Support URL · App Privacy 답안(`docs/store-privacy-labels.md` 를 그대로 옮긴다, 기계가 코드와 대조해 둔 정본이다) · 연령 등급 · **Phased Release 켜기**.

### 심사 통과 후

15. `node scripts/seed-config.mjs --ios <URL>` — 앱스토어 ID 가 나온 뒤에야 가능.
16. **B-14 단계 0**(지인 3~5명) → 크래시 0 확인 → **3일 대기** → 단계 1(15~20명) → 3일 → 단계 2(50명+).
17. 방통위 신고가 아직이면 **여기서 멈춘다**(순서상 이때쯤 나와 있어야 정상이다 — 그래서 1일차에 넣었다).

# [6] 개발 경험 없는 1인 개발자가 놓치기 쉬운, 실제로 큰 문제 3가지

> 고른 기준: **피해 × 확률 × '안 보임'.** 셋 다 이 저장소에 **이미 일어난 전례**가 있다.

---

## ① 「테스트가 그린이다」와 「동작한다」는 다른 말이다 — 이 프로젝트는 **이미 두 번** 겪었다

**전례 1.** 2026-07-26 — `firestore.rules` 가 **런 상세 백업을 전량 거부**하고 있었는데 테스트 **2,052건이 그린**이었다. 테스트가 Firestore 를 목(mock)으로 대체했기 때문이다. *초록불을 보며 죽어 있었다.*

**전례 2.** 2026-07-30 — 안드로이드가 **3주 낡은 JS 번들**로 돌고 있었다. 번들 재생성 명령을 깜빡했는데 **빌드는 성공하고 앱도 정상으로 켜졌다.** 카카오 버튼 로고가 옛 글자 "K" 로 나온 것이 유일한 단서였다.

**지금 정확히 같은 자리에 있는 것 셋:**

| 것 | 상태 | 확인 안 하면 |
|---|---|---|
| **CI** | 설치는 됐는데 **초록 1회가 없다** | 핫픽스가 게이트 없이 나간다. 핫픽스는 정의상 **당황한 상태에서 급하게** 만든다 — 사람 기억에 걸린 게이트는 정확히 그때 빠진다 |
| **Crashlytics·Analytics** | 배선은 확인됐는데 **콘솔 도착은 아무도 안 봤다** | 크래시가 나도 모른다. "배선은 맞는데 콘솔 연결이 끊긴 경우가 흔하다"(`07 부록`) |
| **강제 업데이트 게이트** | 만들었는데 **한 번도 켜본 적 없다** | 유일한 비상 브레이크가 비상 때 처음 작동한다. `config/app` 문서는 프로덕션에 **존재하지도 않는다** |

> **방어는 단순하다.** 셋 다 출시 전에 **"실제로 도착하는 것"까지 한 번씩 본다.**
> CI 는 초록 스크린샷 1장, Crashlytics 는 일부러 낸 크래시 1건, 게이트는 `--min` 을 현재 버전과 같게 넣어 **안 뜨는 것**까지.
> **B-3·B-9·B-10 이 정확히 이것이고, 합쳐서 5.5시간이다.**

## ② 되돌릴 수 없는 것들이 조용히 지나간다 — 지나간 뒤엔 방법이 없다

| 것 | 놓치면 | 지금 할 일 |
|---|---|---|
| **업로드 keystore** (`~/keystores/keego-upload.keystore`) | 잃으면 **그 앱은 영원히 업데이트할 수 없다.** 새 키로는 같은 앱을 갱신 못 하고, 새 앱으로 다시 올려야 한다(리뷰·순위·설치수 전부 초기화). 저장소 **밖**에 있어서 git 이 안 지켜준다 | **안전한 곳 두 군데 이상 백업 + 비밀번호 4개 함께**(`01-store-review-risk A-1` 경고 상자) |
| **App Check enforce 켜는 시점** | 사용자가 생긴 **뒤**에 켜면, 아직 업데이트 안 한 사용자가 잠긴다 | **사용자 0명인 지금이 유일하게 안전한 시점**(B-4) |
| **강제 업데이트 `--min` 켜는 시점** | **고친 버전이 심사를 통과하기 전에** 켜면 사용자는 업데이트할 곳 없이 갇힌다 | 스크립트가 "잠금"을 타이핑하게 해 한 번 막아준다. 그래도 **규칙으로 기억할 것** |
| **첫 코호트 계측** | 출시 후에 붙이면 **최초 코호트를 영구히 잃는다**. 되돌아가서 잴 수 없다 | 이미 `kg_*` 10개 전부 배선됐다 — **지키기만 하면 된다**(끄지 말 것) |
| ~~앱 ID~~ | 스토어에 올리면 영구 고정 | ✅ **잘 지나갔다** — `com.keego.app` 확정(08-03) |
| **Play 재서명 SHA-1** (Android 갈 때) | 등록된 건 업로드 키·debug 키뿐이고, Play 가 재서명에 쓰는 건 **업로드 후에야 생기는 제3의 키**다. 빠뜨리면 **스토어에서 받은 앱만 로그인이 전멸**하고 내부 테스트로는 재현이 안 된다 | Android 착수 시점에 최우선 |

> **공통점:** 전부 "나중에 하면 되는 것"처럼 생겼는데, 나중이 오면 **선택지가 사라진다.**

## ③ 크래시가 **아닌** 고장은 아무도 알려주지 않는다 — 그 침묵이 별 1개로 돌아온다

**Crashlytics 는 크래시만 잡는다.** 그런데 러닝 앱에서 가장 나쁜 고장은 크래시가 아니다 —

- 거리가 실제보다 2배로 찍힌다
- 신발 차감이 안 된다
- 백업이 몇 주째 멈춰 있다 *(→ D-1 조치로 이제는 알려준다. 그 전엔 침묵이었다)*

**이건 크래시가 아니므로 어떤 자동 수단에도 안 잡힌다.** 들어올 경로는 **문의 하나**뿐이다. 그리고 —

> **화가 난 사용자는 문의하지 않는다. 스토어 리뷰에 쓴다.**
> **별 1개는 지울 수 없고, 첫 100명 구간에서는 평점 평균을 통째로 망가뜨린다.**
> 문의함은 **리뷰의 배수관**이다.

이 프로젝트는 그 배수관 입구가 **접힌 아코디언 안에 잠겨 있었다**(`07 L-08` — 로그인이 강제라 사실상 100% 의 사용자에게 4단계 뒤). **08-04 에 밖으로 꺼냈다.** 그건 끝났고, 남은 건 **운영**이다:

| 방어 | 왜 |
|---|---|
| **첫 24시간 안에 답장** | 베타 피드백은 신선도가 전부다. 하루 지나면 상대는 이미 앱을 지웠다 |
| **"고쳤어요"까지 회신** | 제보 → 수정 → *"말씀하신 거 고쳤습니다"* 까지 가면 그 사람은 **전도자**가 된다 |
| **문의 로그를 한 파일에** | 같은 질문 3번 = **UI 결함**. FAQ 10개는 예상이고, 실제 상위 10개는 다를 것이다 — 그 차이가 1.1 우선순위 |
| **단계적 모집(3~5 → 15~20 → 50+, 사이 3일)** | 이게 **구조적 방어**다. 100명이 동시에 들어오면 100명이 동시에 같은 버그를 겪고, 리뷰 100개가 동시에 달리고, 그때 심사 지연(24~48h)과 정면으로 부딪친다. **첫 출시의 가장 흔한 실패는 모집이 성공해서 일어난다** |
| **Phased Release 켜기** | 문제가 보일 때 **심사 없이 배포를 멈출 수 있다.** 첫 출시에 가장 값싼 보험이고 토글 하나다 |
| **쓰지 말 것: 앱테크·앱 리뷰 커뮤니티** | 설치는 늘고 D1 리텐션은 0에 수렴한다. **초기 리텐션 데이터를 오염시켜** 유일하게 정직한 지표를 못 읽게 만든다 |
