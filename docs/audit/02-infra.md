## 1. 읽기 폭탄 — 어디서 몇 번 읽는가

### 1.1 화면 진입마다 컬렉션 전체를 읽는 곳

### 1.2 🟠 `MAJOR` I-1 — `races` 전량 재읽기



`data/races.json` 에 82개 대회가 있고 `scripts/seed-races.mjs` 로 Firestore 에 올라간다.
따라서 **앱 실행 1회 = 82 읽기**다. 하루 3회 실행이면 246 읽기 — 뒤에서 계산하는 하루
총 읽기 260 중 **96%**가 여기서 나온다.

**같은 프로젝트 안에 정답이 이미 있다.** 신발 카탈로그는 똑같은 문제를 이렇게 풀었다:

```ts
// lib/shoeCatalogRemote.ts:13-14 (주석)
//  3) **바뀐 것만 받는다.** 매 실행 500켤레를 읽으면 사용자 수만큼 요금이 는다.
//     마지막으로 본 시각 이후만 조회하고(보통 0건), 받은 건 로컬에 쌓아 캐시한다.
```

대회 목록은 신발 카탈로그보다도 **덜 바뀌는** 데이터다(연 1회 일정 갱신). 그런데 신발은
24시간에 한 번 델타만 받고, 대회는 실행마다 전량을 받는다. **일관성이 깨진 자리다.**

> **추가로 확인이 필요한 점 `[민우 확인]`:** 이 읽기가 **실제로 성공하고 있는지 불확실하다.**
> `races` 규칙은 `allow read: if signedIn()` 인데(`firestore.rules:96`), 위 effect 는 의존성이
> `[]` 라 **마운트 즉시** 돈다. Firebase 인증 복원은 비동기라 그 시점에 `currentUser` 가 아직
> null 일 수 있고, 그러면 읽기는 권한 거부로 실패한 뒤 `catch` 로 삼켜져 시드만 남는다.
> **재시도 경로가 없다.**
> - 실패하고 있다면 → 읽기 비용은 0 이지만 **서버 대회 갱신이 사용자에게 영원히 도달하지 않는다**(기능이 죽어 있다).
> - 성공하고 있다면 → I-1 그대로 읽기 폭탄이다.
>
> **둘 중 무엇이든 문제이고, §7 의 수정안 하나가 양쪽을 다 고친다.** 어느 쪽인지는 실기기에서
> Firestore 사용량 대시보드의 읽기 수를 보면 즉시 갈린다.

## 2. 쓰기 — 어디서 몇 번 쓰는가

### 2.1 🟠 `MAJOR` I-2 — 동기화에 최소 간격이 없다

동기(`runCloudSync`)를 부르는 경로가 **5개**이고, 그중 어느 것도 "방금 했으니 건너뛴다"를
검사하지 않는다.

| # | 트리거 | 위치 | 빈도 |
|---|---|---|---|
| 1 | 부팅(로그인 + 캐시 준비 완료) | `App.tsx:1273` | 실행당 1 |
| 2 | 데이터 변경 디바운스 1.2초 | `App.tsx:1279` | 변경마다 |
| 3 | **AppState `background`** (앱 이탈) | `App.tsx:1295` | 이탈마다 |
| 4 | **AppState `active`** (앱 복귀) | `App.tsx:1295` | 복귀마다 |
| 5 | 당겨서 새로고침 | `App.tsx:774` | 사용자가 당길 때마다 |

가드는 `cloudSyncBusyRef`(동시 실행 방지)뿐이다. **이건 "겹치지 마라"이지 "자주 하지 마라"가
아니다.** 1.2초 간격으로 순차 호출되면 전부 통과한다.

구체적 결과: 사용자가 앱과 카톡을 오가며 30번 전환하면 → **30 읽기 + 30 쓰기**. 데이터는
하나도 안 바뀌었는데도. 배터리와 모바일 데이터도 같이 나간다.

### 2.2 🟡 `MINOR` I-4 — 바뀐 게 없어도 항상 쓴다

```ts
// lib/firebaseCloudPort.ts:309-318
return await runTransaction(getFirestore(), async tx => {
  const snapshot = await tx.get(ref);
  const remote = …;
  const merged = merge(local, remote);
  tx.set(ref, payloadToDoc(merged));   // ← 조건 없음. merged === remote 여도 쓴다.
  return merged;
});
```

원격과 병합 결과가 완전히 같아도 문서를 다시 쓴다. I-2 와 곱해지면 **쓰기의 대부분이 같은
내용의 재기록**이 된다.

추가로, 이 문서는 **사용자의 전체 신발 + 전체 런**이 든 단일 문서다. 즉 매 동기마다
수십~수백 KB 를 통째로 다시 올린다. Firestore 는 문서 크기와 무관하게 쓰기 1회로 과금하지만
**모바일 데이터와 1MiB 문서 상한**은 크기에 정직하게 반응한다.

> 경로를 사이드카로 분리(`stripSyncedRoutes`)해 본문을 줄이는 장치는 이미 들어가 있다
> (`App.tsx:1233`). 그 판단은 옳다 — 여기서 지적하는 건 **빈도**이지 크기가 아니다.

## 3. 비용 추정 — 계산 과정

### 3.1 전제

- **[추정]** 사용자 1명 = 하루 앱 실행 3회 + 러닝 1회. (질문에서 주어진 조건)

  일부만 매일 쓰므로 **이 수치는 상한**이다. 가입자 기준으로는 더 싸진다.
- `races` 컬렉션은 82문서가 시드된 상태로 가정(§1.2 의 `[민우 확인]` 이 "성공" 쪽일 때).

  아래는 전부 선형이라 비율만 곱하면 된다.
  - 읽기 **$0.036 / 100,000건** · 쓰기 **$0.108 / 100,000건** · 저장 **$0.108 / GiB·월**
- 무료 할당량(프로젝트당·하루): 읽기 **50,000** · 쓰기 **20,000** · 삭제 20,000 · 저장 1GiB

| 하루 1회 | 상세 스윕(정상 상태 = 변경 없음) | **0** | **0** |
| | **합계** | **258** | **12** |

> 앱 복귀(`active`) 동기와 당겨서 새로고침은 사용자 습관에 따라 여기에 더 붙는다.
> 보수적으로 빼고 계산했다. **약 260 읽기 / 12 쓰기**로 반올림해 쓴다.

**읽기 258 중 246(96%)이 I-1 하나에서 나온다.**

### 3.3 무료 할당량은 언제 깨지는가

```
읽기 한도 소진:  50,000 ÷ 260 =  192명
쓰기 한도 소진:  20,000 ÷  12 = 1,667명
```

> ### **무료 할당량은 일간 활성 사용자 약 192명에서 깨진다. 읽기가 먼저다.**

### 3.4 월 비용

한 달 30일, 사용자 1명 월 = 읽기 7,800 · 쓰기 360.
무료 할당량 월 환산 = 읽기 1,500,000 · 쓰기 600,000.

**100명**
```
읽기  100 × 7,800 =   780,000  →  무료(1,500,000) 안       → $0
쓰기  100 ×   360 =    36,000  →  무료(600,000) 안         → $0
                                                     합계  →  $0
```

**1,000명**
```
읽기  1,000 × 7,800 = 7,800,000
      과금분 = 7,800,000 − 1,500,000 = 6,300,000
      6,300,000 ÷ 100,000 × $0.036 = 63 × $0.036       = $2.27
쓰기  1,000 ×   360 =   360,000  →  무료 안             = $0
                                                  합계  ≈  $2.3   (약 3,200원)
```

**10,000명**
```
읽기  10,000 × 7,800 = 78,000,000
      과금분 = 78,000,000 − 1,500,000 = 76,500,000
      76,500,000 ÷ 100,000 × $0.036 = 765 × $0.036     = $27.54
쓰기  10,000 ×   360 =  3,600,000
      과금분 = 3,600,000 − 600,000 = 3,000,000
      3,000,000 ÷ 100,000 × $0.108 = 30 × $0.108       = $3.24
저장  [추정] 사용자당 백업 0.1MB + 런 상세 100건 × 30KB ≈ 3.1MB
      10,000 × 3.1MB ≈ 31GB, 과금분 30GB × $0.108      = $3.24
                                                  합계  ≈  $34    (약 47,000원)
```

## 4. 안전장치

### 4.1 무한 루프로 쓰기가 발생할 수 있는 코드 — **발견되지 않음**

가장 의심스러운 자리를 실제로 추적했다. 동기 → 상태 반영 → 시그니처 변화 → 동기 …

```ts
// App.tsx — 디바운스 동기의 의존성
const cloudDataSig = `${shoes.length}:${runs.length}:${Math.max(maxU(shoes),maxU(runs))}:…`;
useEffect(()=>{ … setTimeout(()=>{void runCloudSyncRef.current();},1200); },[authUser?.uid,cloudDataSig]);
```

동기가 끝나면 `applyBackupPayload(merged)` 가 상태를 갱신하고, 그게 `cloudDataSig` 를 바꾸면
1.2초 뒤 또 동기한다. **루프가 될 수 있는 구조다.** 멈추는 이유는 하나뿐이다:

> `mergeRecords`(`lib/cloudSync.ts:210-249`)가 **멱등**이다 — 병합할 때 `updatedAt` 을 새로
> 찍지 않고 큰 쪽을 고를 뿐이다. 그래서 2회차 병합 결과가 1회차와 같고, 시그니처가 고정돼
> 루프가 멎는다.

즉 **수렴은 하지만, 그 근거가 다른 파일에 있는 함수의 성질 하나에 걸려 있다.** 누군가
`mergeCloudData` 계열에 "병합 시각 기록" 같은 걸 한 줄 넣는 순간 **1.2초마다 영구 쓰기**가 된다.
하루 72,000 쓰기 / 사용자다.

**지금 버그는 아니다. 방어선이 얇다는 것이 지적 사항이다.** §7 의 최소 간격 가드(I-2)를 넣으면
이 시나리오의 피해도 같이 상한이 걸린다(1.2초 → 60초, 60배 완화).

## 5. 인덱스 — `firestore.indexes.json` 이 비어 있는 것은 정상이다

```json
{ "indexes": [], "fieldOverrides": [] }
```

**빠뜨린 게 아니다.** 앱의 모든 쿼리를 나열해 대조했다:

| 쿼리 | 형태 | 필요한 인덱스 |
|---|---|---|
| `where('updatedAt','>',커서)` (`services/shoes.ts:110`) | 단일 필드 부등호 | **자동**(단일 필드 인덱스) |
| `orderBy(category,'desc') + limit(100)` (`firestoreRankingStore.ts:74`) | 단일 필드 정렬 | **자동** |
| `where(category,'>',score)` + count (`:90`) | 단일 필드 부등호 | **자동** |
| `getDocs(collection(…))` (races·shoes 전량) | 쿼리 아님 | 불필요 |

**복합 인덱스가 필요한 쿼리(서로 다른 필드의 `where`+`orderBy` 조합)가 하나도 없다.**
Firestore 는 단일 필드 인덱스를 자동 생성하므로 현재 상태로 느려질 쿼리는 없다.

> **1.1 에서 주의할 것:** 리더보드를 재개봉하면서 "이번 달 + 카테고리 정렬" 같은 조합을
> 추가하는 순간 복합 인덱스가 필요해진다. 그때는 **쿼리가 실패하면서 콘솔 링크를 뱉는다** —
> 조용히 느려지는 게 아니라 대놓고 깨지므로, 그 시점에 이 파일을 채우면 된다.

## 6. I-6 — 리더보드 재개봉 시의 읽기 비용(지금은 0)

현재 `firestore.rules:77` 이 `allow read: if false` 라 **모든 읽기가 거부**되고, 거부된 요청은

```ts
// HallOfFameScreen.rn.tsx:158-164 — 카테고리/월이 바뀔 때마다 둘 다 호출
const lb   = await provider.getLeaderboard(category, yearMonth);  // topByCategory(…,100) → 100 읽기
const mine = await provider.getMyRanking(category, yearMonth);    // 아래 참조
```

`getMyRanking` 한 번이 부르는 것(`lib/progression/firestoreRanking.ts:129-152`):

| 호출 | 읽기 |
|---|---|
| `getEntry(uid, ym)` | 1 |
| `countAbove(…)` (`getCountFromServer`) | ~1 |
| `total(ym)` (`getCountFromServer`) | ~1 |
| **`topByCategory(…, 100)` — 위에서 이미 받은 것을 또 받는다** | 100 |

**화면 1회 진입 = 약 203 읽기. 캐시 없음. 탭을 바꿀 때마다 반복.**
사용자가 카테고리 4개를 훑으면 **약 812 읽기** — 지금 하루 예산(260)의 3배를 한 화면에서 쓴다.

절반이 준다. 재개봉 시 §7 의 별도 항목으로 다룬다.

### 11.1 설계에서 지킨 선 — "아끼되, 아껴서 위험해지지는 않는다"

세 조치 모두 **데이터 안전을 비용보다 우선**하도록 판정 방향을 한쪽으로 몰았다.

**I-2 는 시간만으로 막지 않는다.** 시간만 보면 방금 저장한 러닝이 최대 60초 동안 클라우드에
못 올라가고, 그 사이 앱이 죽으면 유실 위험이 생긴다. 그래서 **두 조건을 모두** 만족할 때만
건너뛴다 — ①마지막 성공 동기 이후 로컬 데이터가 하나도 안 바뀌었고 ②60초가 안 지났다.
즉 걷어내는 것은 *올릴 것도 없는데 도는 동기*뿐이고, **바뀐 게 있으면 간격을 무시하고 즉시
올린다.** 여기에 더해 두 경로는 `force` 로 항상 통과시킨다:

- **앱 이탈 직전(`background`)** — 이 호출의 목적이 유실 방지라 아끼면 안 된다
- **당겨서 새로고침** — 사용자가 명시적으로 요청한 행동에 아무 일도 안 일어나면 고장으로 보인다

**I-4 의 비교는 틀려도 안전한 쪽으로만 틀린다.** 같은데 다르다고 판정하면 쓸데없는 쓰기 한
번이고, 다른데 같다고 판정하면 **변경 유실**이다. 그래서 직렬화 실패를 포함해 확신이 없으면
무조건 '다르다'(=쓴다)로 답한다. 원격이 아예 없는 첫 백업도 무조건 쓴다.

**I-3 도 fail-open 이다 — 그리고 이게 가장 중요하다.** 이 게이트가 잘못 켜지면 앱이 통째로
잠기고 사용자가 할 수 있는 일이 없어진다. 그래서 판정이 흔들릴 수 있는 **모든** 지점에서
막지 않는 쪽을 골랐다: 문서를 못 읽으면(오프라인·권한·미링크) 통과, `minSupportedVersion`
이 없거나 형식이 아니면 통과, 버전 비교가 불가하면 통과.

**그리고 차단 결과를 캐시하지 않는다.** 이게 핵심 안전장치다 — 캐시하면 잘못된 값 하나로
오프라인 사용자가 영구히 잠기고, 푸는 방법이 '앱 삭제 후 재설치'밖에 없다. 그건 이 장치가
막으려던 사고보다 나쁘다. 캐시하지 않으므로 **서버에서 값을 되돌리면 다음 실행에 바로 풀린다.**
오프라인 사용자를 못 막는 것은 한계가 아니라 의도다 — 어차피 그들은 데이터를 서버에 올리지도
못한다.

규칙에서 `config` 쓰기는 **아무에게도 열지 않았다**(`allow write: if false`). 여기가 열리면
누구나 `minSupportedVersion` 을 999 로 올려 전 사용자의 앱을 잠글 수 있다 — 공격자 자격으로
직접 확인했다(§11 테스트 표).

**I-1 은 실패와 '변경 0건'을 구분한다.** 조회 실패는 `null`(캐시 유지), 변경 없음은 빈 배열이다.
이 구분이 없으면 오프라인 한 번에 캐시가 비워진다. 실패해도 *시도 시각*은 남겨 매 실행
재시도하지 않는다.

### 11.2 부수 효과 — 죽어 있었을 가능성이 있던 기능이 살아난다
