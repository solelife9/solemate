# 클라우드 데이터 모델 재설계 — 소셜·랭킹·커뮤니티까지 버티는 구조

> 2026-08-01 설계 · 승인 대기 · 작성자: Claude(모바일 동기화 관점)
> 선행: `docs/audit/03-data-integrity.md`(D-1~D-4) · `docs/data-schema.md` · `MISSION.md`
>
> **범위:** 클라우드 저장 구조를 "문서 하나짜리 덩어리"에서 "레코드 하나 = 문서 하나"로 바꾼다.
> **로컬-퍼스트는 유지한다**(폰이 원본). 왜 유지해도 되는지는 §2 가 답한다.
>
> ⚠️ **이 문서는 계획이다. 코드는 아직 하나도 바뀌지 않았다.** 승인 후 §7 순서로 진행한다.

## 용어 — 이 문서에서 「덩어리」란

지금 클라우드에는 사용자 데이터가 **문서 딱 하나**로 들어 있다. 신발·러닝·설정·진척·메달이
전부 그 안의 배열이다. 러닝 하나를 추가해도 **그 문서 전체를 다시 쓴다.**
이 문서에서 「덩어리(blob)」는 그 단일 문서를 가리킨다.

```
지금:  📄 userBackups/{uid}  ← 신발 12 + 러닝 300 + 설정 + 진척 + 메달  (전부 한 장)
목표:  📁 userBackups/{uid}
         ├ 📄 (설정·진척)          작은 종이 한 장
         ├ 📁 runs/    📄 📄 📄 …   러닝 한 건 = 종이 한 장
         └ 📁 shoes/   📄 📄 …
```

> **"덩어리를 없애나?"** — 없애는 게 아니라 **다이어트된다.** 나누고 나면 남는 건 설정·진척뿐인
> 몇 KB짜리 작은 문서이고, 그건 더 쪼갤 이유가 없다(어차피 한 번에 읽고 쓰는 값들이다).
> 즉 목표는 "문서를 없애는 것"이 아니라 **"문서가 무한정 자라지 않게 하는 것"** 이다.

## 0. 왜 지금인가

민우님이 소셜·랭킹·커뮤니티·같이 달리기를 **만들기로 확정**했고, 출시일이 밀려도 좋다고 했다.
그렇다면 지금이 가장 싼 시점이다 — **사용자가 사실상 0명**이라 마이그레이션 비용이 앞으로
영원히 지금보다 비싸진다. 그리고 목적지를 아는데 다른 데로 짓는 건 낭비다.

지금 구조의 한 줄 진단:

```
userBackups/{uid}  ←  문서 딱 1개 안에 신발·러닝·설정·진척·메달이 전부 배열로
```

**클라우드 사본이 데이터베이스가 아니라 덩어리(blob)다.** 여기서 오는 문제가 이미 두 번
터졌고(경로로 한 번, 묘비로 한 번 — 둘 다 1MiB 천장), 소셜을 얹으면 **구조적으로 막힌다**(§3).

---

## 1. 목표와 비목표

**목표**
1. 러닝이 수만 건 쌓여도 안 터진다 (1MiB 천장 제거)
2. 서버가 사용자 기록을 **조회**할 수 있다 (랭킹 서버 재계산 · 신발 통계 집계)
3. 러닝 한 건을 **개별적으로 공유**할 수 있다 (피드·친구 공유)
3b. **공개 프로필과 랭킹에 신발을 붙일 수 있다** — keego 만 할 수 있는 조합(§3.35·§3.36)
4. 동기 비용이 지금보다 **늘지 않는다** (AUDIT 2 에서 43배 줄인 것을 지킨다)
5. 시계 어긋남 문제(D-2)를 **완전히** 푼다
6. 오프라인·즉시 열림·배터리 — 지금 장점을 하나도 잃지 않는다

**비목표(이번에 안 한다)**
- 소셜 기능 자체 구현 — **자리만 확보**하고 만들지 않는다
- 웹 앱
- 개인 저장소를 남에게 여는 것 — **영원히 안 한다**(§2.3)

## 2. 「폰이 원본」을 유지해도 되는가 — 확실합니다, 단 조건이 있습니다

민우님 질문에 정면으로 답한다.

### 2.1 답: 유지한다. 개인 데이터에 한해서.

**로컬-퍼스트는 "내 데이터"에만 적용되는 규칙이다.** 내 러닝, 내 신발, 내 설정 —
쓰는 사람이 나 하나이고, 오프라인에서도 되어야 하고, 앱을 열면 즉시 보여야 하는 것.

**소셜·랭킹·커뮤니티·같이 달리기는 애초에 다른 종류의 데이터다.** 여러 사람이 쓰고,
서버가 계산하고, 실시간이어야 한다. **거기엔 로컬-퍼스트를 적용하지 않는다** — 처음부터
서버가 원본이다.

즉 이건 양자택일이 아니라 **데이터 종류별로 다른 규칙**이다.

| 데이터 | 원본 | 이유 |
|---|---|---|
| 내 러닝·신발·설정 | **폰** | 단일 작성자. 산속에서도 기록돼야 함. 즉시 열려야 함 |
| 내가 공개한 게시물 | **서버** | 남이 읽음. 내 폰이 꺼져 있어도 보여야 함 |
| 랭킹 점수 | **서버** | 서버가 계산해야 조작을 막음 |
| 같이 달리기 세션 | **서버** | 실시간 다자 상태. 폰이 원본일 수 없음 |
| 신발 커뮤니티 통계 | **서버** | 여러 사람 데이터의 집계 |

### 2.2 그런데 지금 구조로는 저 표를 지킬 수 없다

**덩어리이기 때문이다.** 러닝 한 건을 친구에게 보여주려면 그 러닝이 개별적으로 읽혀야 하는데,
지금은 러닝이 **체중·나이·안정시심박·전체 기록이 든 덩어리 안**에 있다. 열어줄 방법이 없다.

그래서 이번 재설계는 **"폰이 원본"을 포기하는 게 아니라, 그걸 계속 유지하기 위해 필요한 작업**이다.
덩어리를 그대로 두면 소셜을 붙이는 순간 "그냥 서버-퍼스트로 갈아엎자"는 압력이 온다.

### 2.3 절대 어기지 않을 선 — 개인 저장소와 공개 저장소의 분리

> **`userBackups/{uid}` 는 영원히 본인만 읽는다. 남에게 여는 일은 없다.**
> 공유는 **"내가 공개하기로 한 것만 따로 복사해 올리는"** 별도 컬렉션으로 한다.

keego 는 이 실수를 이미 한 번 했다 — 동의도, 화면도 없는데 닉네임과 월간 운동량이 전원
읽기 가능한 컬렉션에 쌓이고 있었다(`767032e`, AUDIT 1). **같은 실수를 두 번 하지 않기 위해
구조로 막는다.**

공개 복사본은 **필요한 필드만** 담는다(거리·시간·페이스·신발명). 경로·심박·위치는
사용자가 명시적으로 켰을 때만.

## 3. 소셜·랭킹·커뮤니티·같이 달리기가 오면 무엇이 필요한가

민우님이 만들겠다고 한 것들을 하나씩 놓고, **지금 구조에서 되는지 / 재설계 후 되는지**를 본다.

| 기능 | 지금 구조 | 재설계 후 | 왜 |
|---|---|---|---|
| 친구와 기록 공유 | ❌ **불가** | ✅ | 러닝이 개별 문서라 공개본을 만들 수 있다 |
| 월간 랭킹(현재 설계) | ⚠️ 되지만 **조작 가능** | ✅ | 서버가 러닝을 조회해 재계산 가능 |
| 피드 | ❌ **불가** | ✅ | 위와 같음 |
| 신발 커뮤니티 데이터 | ⚠️ 매우 비쌈 | ✅ | 신발이 개별 문서라 집계 가능. 지금은 사용자마다 1MiB 덩어리를 통째로 읽어야 함 |
| **공개 프로필**(무슨 신발 신나) | ❌ **불가** | ✅ | 신발을 개별로 꺼내 공개 미러를 만들 수 있다 |
| **랭킹 × 신발**(1·2·3위는 뭘 신나) | ❌ **불가** | ✅ | 서버가 그 달 신발을 조회해 엔트리에 담는다. 추가 읽기 0 |
| 같이 달리기(**비실시간**) | ❌ 불가 | ✅ | 각자 평소대로 달리고 결과만 모아 비교. 새 원시 요소 없음(§3.4) |

### 3.1 랭킹 — 서버 재계산이 핵심

지금은 **폰이 계산한 점수를 서버가 그대로 믿는다.** 규칙 주석에 이미 "1.1 재개봉 시 서버
재계산 필요"라고 박혀 있다(`firestore.rules:87`). 안 그러면 점수를 조작할 수 있다.

서버가 재계산하려면 사용자 러닝을 읽어야 한다.
- **지금:** 1MiB 덩어리를 통째로 읽고 메모리에서 이번 달 것만 걸러야 한다. 사용자 1만 명이면
  매달 1만 개의 덩어리를 읽는다.
- **재설계 후:** `where('date','>=', 이번달)` 한 방. 필요한 것만 읽는다.

> **정직한 한계:** 서버가 재계산해도 **원본 데이터는 폰이 올린 것**이다. 조작된 앱이 가짜
> 러닝을 올리는 것까지는 못 막는다. 이건 스트라바·가민도 같다(GPS 조작은 그쪽도 못 막는다).
> 막을 수 있는 건 "점수 계산식을 속이는 것"이고, 그건 서버 재계산으로 막힌다.
> 그 위는 서버 쪽 이상 탐지(비현실적 페이스·순간이동)로 잡는데, 그것도 **러닝을 조회할 수
> 있어야** 가능하다.

### 3.2 피드·공유

```
shared/{postId}
  ownerUid, visibility('public'|'followers'|'link'), createdAt(server),
  runId, distanceKm, durationSec, paceSec, shoeName, thumbUrl?, routeSummary?
```

**개인 저장소에서 필요한 것만 복사**해 만든다. 원본 러닝을 참조만 하는 게 아니라 복사하는
이유: 원본을 지워도 공개본이 깨지지 않아야 하고, 반대로 공개본을 지워도 원본은 남아야 한다.
**두 생명주기는 독립이다.**

### 3.3 신발 커뮤니티 데이터 — keego 의 해자

"이 신발 실제 평균 수명 640km, 사용자 1,240명" 같은 것. **경쟁 앱이 못 하는 것**이고
`MISSION.md` 의 차별점과 직결된다.

```
shoeStats/{shoeId}   ← Cloud Function 이 집계해 씀. 클라이언트는 읽기만
  sampleCount, medianRetireKm, p25, p75, updatedAt
```

집계하려면 서버가 **여러 사용자의 신발 데이터를 읽어야** 한다. 신발이 개별 문서면 쉽고,
덩어리면 사용자마다 전체를 읽어야 해서 사실상 불가능하다.

> ⚠️ **동의가 먼저다.** 익명 통계라도 내 신발 사용 데이터가 집계에 들어가는 것이므로
> 처리방침에 명시하고 옵트인을 받는다. AUDIT 1 의 교훈.

### 3.35 공개 프로필 — 「이 사람은 무슨 러닝화 신나」

민우님이 추가로 제시한 방향이고, **keego 가 해야 할 소셜의 정답에 가깝다.** 스트라바 피드를
복제하는 게 아니라 **신발 중심 소셜** — 남들이 뭘 신고 얼마나 달렸는지 보이는 것. 그건
경쟁 앱에 없고 `MISSION.md` 의 shoe-first 정체성 그대로다.

```
profiles/{uid}                     ← 남들이 읽는다. 공개 미러
  nickname, photoUrl, updatedAt(server)
  activeShoes: [{name, brand, usedKm, maxKm, category}]   ← "지금 신는 신발"
  stats: {monthKm, totalKm, runCount}
  hallOfFame: [{name, retiredAtKm, grade, year}]          ← 은퇴한 신발
  visibility: 'public' | 'followers' | 'private'
```

**개인 저장소를 여는 게 아니다.** 공개하기로 한 것만 **따로 복사해 올린다.**
체중·나이·안정시심박·GPS 경로·메모는 **넘어가지 않는다**(§2.3 의 선).

이 기능이 데이터 모델에 요구하는 것:
- **신발이 개별 문서여야** 프로필 미러를 만들기 쉽고, 나중에 "이 신발 신는 사람 N명"
  (`shoeStats`) 집계로 이어진다. 덩어리에 묻혀 있으면 둘 다 어렵다
- 프로필 미러는 **동기 때 갱신**한다(신발·통계가 바뀌었을 때만). 실시간일 필요 없다
- **스펙은 미러에 담지 않는다.** 무게·스택·드롭은 보는 사람 앱이 번들 카탈로그에서 붙인다
  (§3.36 과 같은 원칙) — 미러가 작아지고, 스펙이 갱신되면 과거 프로필까지 자동으로 최신이 된다
- `visibility` 기본값은 **비공개**. 사용자가 켜야 보인다(AUDIT 1 의 교훈 — 동의 없이
  공개되던 사고를 두 번 만들지 않는다)

> 이 방향이면 **피드(§3.2)보다 프로필이 먼저**여도 된다. 피드는 "무엇을 했나"의 흐름이고,
> 프로필은 "이 사람은 어떤 러너인가"의 정지 화면이다. keego 의 차별점은 후자에 가깝다.

### 3.36 랭킹 × 신발 — 「1, 2, 3위는 뭘 신나」

민우님이 짚은 것 중 **제품적으로 제일 강한 조합**이다. 랭킹은 어디에나 있고 신발 관리도
어딘가엔 있지만, **둘을 붙인 곳은 없다.** "상위 랭커들이 뭘 신는가"는 러너가 실제로 궁금해하는
질문이고, keego 말고는 답할 수 있는 앱이 없다(신발과 기록을 한 곳에서 갖는 앱이 없으니까).

**구현: 랭킹 엔트리에 신발 요약을 함께 담는다(비정규화).**

```
leaderboards/{연월}/entries/{uid}
  uid, nickname, rankTier, progressPoints, distance, ...   ← 기존
  shoes: [{brand, model, usedKm}]   ← ★ 추가. 그 달에 실제로 신은 신발
```

왜 따로 읽지 않고 **엔트리 안에 넣는가**: 랭킹 화면은 어차피 상위 100명 엔트리를 읽는다.
신발을 거기 담아두면 **추가 읽기가 0** 이다. 프로필을 따로 읽으면 100명 × 1읽기가 더 붙는다.
AUDIT 2 에서 읽기를 43배 줄여 놓고 여기서 되돌릴 이유가 없다.

**신발 스펙은 저장하지 않는다.** 무게·스택·드롭은 보는 사람의 앱이 **번들 카탈로그에서 붙인다**
(`data/shoeSpecs.json` — 이미 앱에 들어 있다). 그래서:
- 공개 미러가 작게 유지된다(브랜드·모델 이름만)
- 스펙이 갱신되면 **과거 랭킹까지 자동으로 최신**이 된다
- "스펙 좋네" 비교가 기존 신발 비교 화면을 그대로 재사용한다

> **이건 서버가 써야 한다.** 클라이언트가 쓰면 "내가 신은 신발"도 조작할 수 있다.
> §3.1 의 서버 재계산이 점수와 신발을 **함께** 계산해 넣는다.

### 3.4 같이 달리기 — **비실시간으로 확정**(2026-08-01 민우님)

> "같이 달리고 나중에 비교해도 되고, 각자 다른 시간에 달리고 다른 사람 기록 확인도 되고"

**실시간이 아니다.** 이 한 마디로 설계가 크게 단순해지고 위험 두 건이 사라진다:

- ❌ 실시간 리스너(`onSnapshot`) — **안 들인다.** 저장소 전체 0건 규율이 유지된다
  (AUDIT 2 에서 "비용 관점에서 가장 잘된 설계 결정"이라고 적은 것)
- ❌ 실시간 위치 공유 — 안 한다. 가장 민감한 데이터를 아예 다루지 않는다
- ❌ 세션 TTL·매회 동의 — 필요 없다

남는 건 **이미 설계한 것들의 조합**이다. 새 원시 요소가 없다.

```
groupRuns/{groupRunId}
  hostUid, title, scheduledAt, targetKm?, visibility, memberUids[]
groupRuns/{groupRunId}/results/{uid}
  runId, distanceKm, durationSec, paceSec, shoeName, finishedAt(server)
  ← 각자 자기 러닝을 평소대로 기록하고, 끝난 뒤 결과만 올린다
```

동작:
1. 누가 "이번 주말 10km" 를 만든다 → 친구들이 참가
2. **각자 편할 때 평소처럼 달린다**(같은 시간이어도, 아니어도 됨). 러닝 기록 경로는 **하나도 안 바뀐다**
3. 끝나면 결과를 올린다 → 비교 화면에서 나란히 본다

**읽기 비용:** 비교 화면을 열 때 참가자 수만큼(보통 2~10). 화면을 열 때만. 리스너 없음.

> **이게 keego 답다.** 실시간 추적은 안전·프라이버시 부담이 크고 배터리도 먹는데,
> 정작 러너가 원하는 건 "같이 달렸다는 느낌"과 "끝나고 비교"다. 후자만 취한다.
> 나중에 실시간이 정말 필요해지면 그때 `liveSessions/` 를 별도로 얹으면 되고,
> **지금 구조는 그걸 막지 않는다.**

"다른 사람 기록 확인"은 §3.35 공개 프로필과 §3.2 공개본이 이미 담당한다 — 별도 설계 불필요.

## 4. 새 구조

```
userBackups/{uid}                       ← 개인 저장소. 영원히 본인만.
  ├─ (문서 본문)  settings · progression · 프로필      작게 유지
  ├─ runs/{runId}          러닝 1건 = 문서 1개          ★ 이번 작업
  ├─ shoes/{shoeId}        신발 1켤레 = 문서 1개        ★ 이번 작업
  ├─ medals/{medalId}      메달 1개 = 문서 1개          ★ 이번 작업
  └─ runDetails/{runId}    경로·심박·구간 (이미 이 모양)

profiles/{uid}                          ← 나중. 공개 프로필(「무슨 신발 신나」)
shared/{postId}                         ← 나중. 공개하기로 한 것만
groupRuns/{groupRunId}                  ← 나중. 같이 달리기(비실시간)
leaderboards/{연월}/entries/{uid}       ← 이미 있음. 서버가 계산하도록 전환
shoeStats/{shoeId}                      ← 나중. 커뮤니티 집계
shoes/{shoeId} · races/{raceId} · config/app   ← 이미 있음(전역 카탈로그)
```

**규칙은 이미 준비돼 있다.** `userBackups/{uid}/{document=**}` 재귀 매치가 본인만 읽고 쓰게
덮고 있어서(`firestore.rules:57-60`) 하위 컬렉션이 늘어도 규칙 변경이 필요 없다.

### 4.1 레코드 문서 모양

```ts
// userBackups/{uid}/runs/{runId}
{
  // ── 동기 메타 ──
  updatedAt: serverTimestamp(),  // 서버가 찍는다. **델타 조회의 커서**
  editedAt: number,              // 기기가 찍는다(보정 시계). **충돌 판정(LWW) 기준**
  deleted?: true,                // 묘비. 문서는 남고 본문만 비운다(§4.3)
  // ── 본문 ──
  shoe_id, km, run_date, duration, cadence, heart_rate,
  elevation_m, calories, location, memo, source, run_time
  // route 는 여기 없다 — runDetails 가 갖는다(이미 그렇게 분리돼 있음)
}
```

**시각 필드가 두 개인 게 핵심이다.** 하나로 못 한다:

| 필드 | 누가 찍나 | 무엇에 쓰나 | 왜 이게 필요한가 |
|---|---|---|---|
| `updatedAt` | **서버** | 델타 조회 커서 | 기기 시계를 못 믿으니 커서는 서버 시각이어야 한다 |
| `editedAt` | **기기**(보정 시계) | 충돌 시 누가 이기나 | "서버에 늦게 도착한 쪽"이 아니라 **"실제로 나중에 고친 쪽"** 이 이겨야 한다 |

`updatedAt` 만 쓰면 오프라인에서 3일 전에 고친 게 나중에 올라와서 오늘 편집을 덮는다.
`editedAt` 만 쓰면 기기 시계가 어긋날 때 무너진다(= 지금 D-2 문제).

> **D-2 가 여기서 완전히 풀린다.** AUDIT 3 에서 만든 시계 보정(`lib/clockOffset`)이 버려지지
> 않고 `editedAt` 의 근거가 된다. 그리고 서버 시각을 문서마다 직접 박을 수 있게 돼(배열
> 원소가 아니므로) 커서는 아예 흔들리지 않는다.

### 4.2 필드별 병합 — 단순 LWW 가 아닌 것 하나

대부분 LWW(`editedAt` 큰 쪽)면 된다. 예외 하나:

**`usedKmHighWater`(신발 최고수위)는 `max()` 로 합친다.** 단조 증가 값이라 LWW 로 하면
기록이 덜 실린 기기가 나중에 쓸 때 수위가 깎인다 — 그러면 D-4 의 감지가 무력해진다.

### 4.3 삭제

문서를 **바로 지우지 않는다.** `deleted:true` + 본문 비우기 + `updatedAt` 갱신.

이유: 델타 조회는 "커서 이후 바뀐 문서"를 가져오는데, 문서를 지워버리면 **다른 기기가 삭제
사실을 알 방법이 없다**(조회 결과에 안 나온다). 묘비가 있어야 삭제가 전파된다.

TTL(90일) 후 소유 기기가 진짜로 지운다 — AUDIT 3 D-1 에서 만든 규칙을 그대로 쓴다.
다만 이제 묘비가 **본문 안 배열이 아니라 독립 문서**라 덩어리를 밀어 올리지 않는다.

## 5. 동기 프로토콜

### 5.1 읽기 경로는 안 바뀐다 — 이게 비용의 핵심

> **화면은 클라우드를 읽지 않는다. 로컬 캐시만 본다.**

이 규칙을 지키는 한 클라우드 읽기는 **화면 사용량과 무관**하다. 앱을 100번 열어도 읽기는
안 는다. 지금도 그렇고, 바뀐 뒤에도 그렇다. (AUDIT 2 에서 43배 줄인 것이 이 규칙 덕이다.)

### 5.2 델타 동기

```
PULL   각 컬렉션마다:  where('updatedAt', '>', 커서).orderBy('updatedAt').limit(500)
       → 받은 문서를 로컬에 병합, 커서를 최대 updatedAt 으로 전진
PUSH   로컬 dirty 목록의 문서만 writeBatch 로(최대 500건씩)
```

- **인덱스:** `updatedAt` 단일 필드 → **자동 생성.** 복합 인덱스 불필요
- **dirty 추적:** 로컬 변경 시 `dirtyIds` 에 id 추가(레코드 영속과 같은 durable 단계에서),
  push 확인 후 제거. 크래시해도 다음 부팅에 재시도된다
- **pending write 주의:** 내가 방금 쓴 문서는 서버 확인 전까지 `updatedAt` 이 null 이다.
  커서 계산에서 null 은 건너뛴다(다음 동기에 잡힌다)

### 5.3 비용 비교

| 상황 | 지금 | 재설계 후 |
|---|---|---|
| 동기 1회(변경 없음) | 읽기 1 | 읽기 3 (runs·shoes·medals 각 1) |
| 동기 1회(러닝 1건 추가) | 읽기 1 + 쓰기 1 **(전체 재업로드)** | 읽기 3 + 쓰기 1~2 **(바뀐 것만)** |
| 재설치 복원(러닝 1,000건) | 읽기 1 | 읽기 ~1,000 (평생 몇 번) |
| 서버 랭킹 재계산 | 사용자당 덩어리 1개 통째 | 이번 달 것만 조회 |

**읽기가 1 → 3 으로 는다.** 하루 4회 동기면 사용자당 하루 +8 읽기다.
AUDIT 2 후 하루 약 6 읽기였으니 **약 14 로 는다** — 무료 한도 기준 8,300명 → 약 3,500명.

> **이 대가를 치를 가치가 있는가:** 있다. 쓰기가 크게 줄고(전체→부분), 1MiB 천장이 사라지고,
> 소셜·랭킹·커뮤니티가 **가능해진다**. 그리고 3,500명 시점의 월 비용은 여전히 $0 대다.
>
> **줄이는 방법도 있다(선택):** 세 컬렉션을 `records/{id}` 하나로 합치고 `type` 필드로 구분하면
> 읽기가 다시 1 이 된다. 대신 문서 모양이 섞여 규칙·쿼리가 덜 깨끗해진다.
> **권장하지 않는다** — 하루 8 읽기를 아끼자고 모델을 흐리는 건 남는 장사가 아니다.

## 7. 이행 계획 — 단계마다 되돌릴 수 있게

**한 번에 갈아엎지 않는다.** 각 단계 끝에 게이트(`tsc`·`lint`·`test`·규칙) + 실기기 확인.

| 단계 | 무엇 | 끝나면 확인할 것 | 되돌리기 |
|---|---|---|---|
| **0** | 설계 승인 · 테스트 골격 · 규칙 확인 | — | — |
| **1** | 레코드를 **하위 문서로도** 쓴다(덩어리에도 계속 씀). 읽기는 아직 덩어리 | 두 곳의 내용이 같은가(자동 대조 테스트) | 하위 문서 쓰기만 끄면 끝 |
| **2** | 읽기를 하위 문서 **델타**로 전환. 쓰기는 여전히 양쪽 | 재설치 복원이 온전한가 · 두 기기 동기 | 읽기를 덩어리로 되돌림 |
| **3** | 덩어리에서 러닝·신발·메달 제거 (설정·진척만 남김) | 1MiB 여유 · 기존 사용자 이관 | ⚠️ 여기서부터 되돌리기 비쌈 |
| **4** | 서버 랭킹 재계산(Cloud Function) — 소셜의 첫 조각 | 조작 시도 차단 | 플래그로 끔 |

**단계 1~2 가 안전망이다.** 이 구간에서는 언제든 옛 경로로 돌아갈 수 있고, 두 저장소의
내용을 기계적으로 대조할 수 있다. 이 프로젝트는 이미 이 패턴을 썼다 — 경로를 사이드카로
뺄 때 *"새 집에 짐이 들어간 것을 확인하기 전에 옛 집을 비우면 그게 유실이다"*(`runDetailSync`).

### 7.1 기존 사용자 이관

지금 실사용자는 사실상 민우님과 테스트 계정뿐이다. 그래도 **코드로 처리한다** — TestFlight
사용자가 있을 수 있고, 무엇보다 이관 코드는 한 번 쓰면 재사용된다.

- 단계 1 에서 **최초 동기 시 덩어리 → 하위 문서 복사**(멱등). 실패하면 다음 동기에 재시도
- 덩어리는 단계 3 까지 **손대지 않는다**
