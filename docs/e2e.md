# E2E 테스트 (Maestro)

## 왜 넣었나

2026-08-07, 갤럭시 S10e 에서 기록 상세를 열고 시스템 뒤로가기를 눌렀더니 목록으로
돌아가는 게 아니라 **앱이 통째로 종료됐다.** 저장소 전체에 `BackHandler` 가 0건이었다.

**단위 테스트 3,500개가 이걸 못 잡았다 — 잡을 수가 없다.** 버그가 "JS 함수의 반환값"이
아니라 "OS 버튼이 앱에 도달하는가"에 있었기 때문이다. 그 층을 검사하는 수단이 없었고,
그게 E2E 를 넣은 이유다.

## 실행

```bash
npm run e2e             # 안드로이드 실기기, 전체(번호 순)
npm run e2e -- ios      # 아이폰 — ⚠️ 현재 실행 불가(아래 한계 참조)
npm run e2e -- 02       # 이름에 '02' 가 든 흐름만
npm run e2e -- ios 02   # 둘 다
```

- **안드로이드**: USB 로 기기를 연결하고 **화면을 켜서 잠금을 풀어 둔다.**
- **아이폰**: ⚠️ **현재 실행 불가.** 시뮬레이터도 실기기도 막혀 있다
  (아래 '알려진 한계' — ML Kit + Maestro 실기기 미지원). 흐름 파일은 준비돼 있고,
  둘 중 하나가 풀리는 날 그대로 돌아간다.

## 도구 선택 — 왜 Maestro 인가

RN E2E 의 표준은 Detox 와 Maestro 둘인데 이 저장소엔 Maestro 가 맞다.

| | Maestro | Detox |
|---|---|---|
| 네이티브 변경 | **없음** | 앱에 테스트 러너를 심어야 함 |
| 검사 대상 | **릴리스 APK 그대로** | 전용 테스트 빌드 |
| 흐름 작성 | YAML | JS |

이 프로젝트는 **네이티브 의존성 사전 승인제**라 첫 줄의 차이가 크다. 그리고 실제로
스토어에 올릴 바이너리를 그대로 검사한다는 점도 Detox 에는 없는 이점이다.
Expo 공식 권장도 Maestro 다.

설치: `brew tap mobile-dev-inc/tap && brew install maestro` (Java 17+ 필요)

## 흐름 목록

| 흐름 | 덮는 것 | 플랫폼 |
|---|---|---|
| `00-smoke` | 부팅 → 홈 렌더. 이게 깨지면 나머지 실패는 전부 무의미하다 | 공통 |
| `01-tabs` | 네 탭 전부 열림 = 네 화면의 **첫 마운트**를 한 번씩 밟는다 | 공통 |
| `02-back-navigation` | **그 버그의 회귀 테스트.** 상세 → 목록 (+ 안드로이드는 탭 → 홈 → 종료) | 공통(뒷단계만 안드로이드) |
| `03-run-start-cancel` | 홈 CTA → 목표 화면 → 뒤로가기 복귀 | 공통 |
| `04-shoe-detail` | 신발 상세 열림/닫힘 — `lib/backStack` 이 실제로 걸렸는지 확인하는 유일한 경로 | 공통 |
| `05-back-button` | 화면 안 `‹` 버튼(기록 상세 · 공용 헤더 · 목표 화면) | 공통 |

## 뒤로가기는 플랫폼마다 **물리적으로 다른 동작**이다

이게 이 스위트에서 제일 헷갈리는 부분이라 따로 적는다.

| | 주 수단 | 구현 |
|---|---|---|
| 안드로이드 | **하드웨어 뒤로가기 버튼** | OS → `BackHandler` → `lib/backStack` |
| 아이폰 | **왼쪽 가장자리 스와이프** | `primitives.SwipeBack` 의 PanResponder |
| 공통 | 화면 안 `‹` 버튼 | 각 화면의 `onBack` |

셋은 구현이 전부 달라서 **하나가 살아 있어도 다른 하나가 죽을 수 있다** — 실제로
안드로이드에서 `‹` 버튼은 멀쩡한데 하드웨어 뒤로가기만 통째로 없던 게 2026-08-07 버그다.

흐름 파일을 플랫폼별로 복제하지 않는다(둘이 반드시 어긋난다). 다른 건 '뒤로 가는 동작'
한 줄뿐이므로 `.maestro/subflows/back.yaml` 하나로 모으고, 거기서만 분기한다.

⚠️ **아이폰 스와이프 좌표는 아무 데서나 시작하면 안 된다.** `SwipeBack` 인식 조건이 빡빡하다
(`primitives.tsx`): 왼쪽 가장자리 **24pt 안**에서 시작 · 거의 완전한 수평 · 화면폭 1/3 이상.
서브플로우는 3%(가장 좁은 iPhone SE 375pt 에서도 11pt)에서 시작한다.
`__tests__/e2eFlowSelectors.test.ts` 가 이 값과 소스 임계값을 함께 감시한다 —
좌표를 키우면 제스처가 **조용히** 안 먹고 "화면이 안 닫힘"으로 애매하게 실패하기 때문이다.

## 지키는 규칙

### 1. 흐름은 비파괴다
실기기(민우님 폰)에서 도는 흐름이라 **러닝을 만들지도, 기록을 지우지도, 신발을
등록하지도 않는다.** `__tests__/e2eFlowSelectors.test.ts` 가 파괴적 선택자가 흐름에
들어오는 것을 막는다.

데이터를 만드는 검증이 필요하면 별도 디렉터리로 분리하고 에뮬레이터 전용으로 표시할 것.

### 2. 짧은 타이머와 경주하지 않는다
처음엔 03 이 카운트다운(3초)까지 들어갔다가 '취소'를 누르는 흐름이었는데, 실기기에서
**UI 자동화 왕복이 카운트다운보다 느려 그대로 러닝에 진입했다.** 0.00km · 25초짜리
유령 기록이 남았고 그 복구 다이얼로그가 나머지 흐름 4개를 전부 막았다.

이기더라도 기기가 느린 날 진다. 그리고 지는 날엔 유령 기록이 남는다 — 이 앱은 가짜
기록이 프로필의 「1km 최고」를 차지했던 사고를 이미 겪었다(`lib/vehicleDetect.ts`).

### 3. 한 번에 하나씩 돈다
`maestro test .maestro/flows/` 로 디렉터리를 통째로 넘기면 흐름들이 같은 앱을 두고
서로 밟는다. `scripts/e2e.sh` 가 순서를 고정한다.

### 4. 선택자는 카피가 아니라 `testID`
탭바를 `"기록"` 같은 사용자 문구로 잡으면 카피를 고칠 때마다 E2E 가 깨진다.
`.maestro/` 는 전부 `id:`(= `testID`)로 잡고, `__tests__/e2eFlowSelectors.test.ts` 가
**흐름이 참조하는 id 가 소스에 실제로 있는지**를 `npm test` 에서 검사한다.
E2E 는 기기가 있어야 돌아서, 이 가드가 없으면 선택자가 조용히 썩는다.

## 알려진 한계

### 로그인 게이트 — CI 자동화가 막혀 있다
앱은 로그인이 필수이고 **소셜 로그인 4종(구글·애플·카카오·네이버)만** 지원한다.
이메일/비밀번호 계정이 없어서 갓 초기화한 에뮬레이터에서는 자동으로 로그인할 수 없다.
그래서 흐름들은 `clearState: false` 로 **이미 로그인된 기기**를 전제하고, 로그인 화면이
뜨면 `assertNotVisible: login-screen` 으로 **이름을 붙여 실패**한다(조용히 통과하지 않는다).

CI 에서 돌리려면 셋 중 하나가 필요하다:
1. **Firebase Auth 에뮬레이터** + 테스트 계정 — 표준이지만 앱이 에뮬레이터를 가리키게
   하는 빌드 분기가 필요하다.
2. **E2E 전용 빌드 변형**에서만 도는 인증 시드.
3. 로그인된 에뮬레이터 스냅샷을 CI 에 굽기.

셋 다 **인증 경로를 건드린다 — 보안 영향이 있어 민우님 승인 없이 넣지 않았다.**
지금은 로컬 실기기 실행만 지원한다.

### ⚠️ 아이폰은 **시뮬레이터로 못 돌린다** — 애플 실리콘 + ML Kit

시뮬레이터로 하려다 막혔고, 이건 설정 문제가 아니라 **구조적 제약**이라 적어 둔다.
다음 사람이 같은 길로 다시 들어가지 않게.

`GoogleMLKit`(메달·기록증 OCR)이 **arm64 시뮬레이터 슬라이스를 제공하지 않는다.**
`ios/Pods/MLKitCommon/Frameworks/MLKitCommon.framework` 실측:

```
x86_64 → iOS 시뮬레이터
arm64  → iOS 기기          ← 시뮬레이터용 arm64 가 없다
```

그래서 Pods 가 `EXCLUDED_ARCHS[sdk=iphonesimulator*] = arm64` 를 강제한다(실수가 아니라
필수다 — 지우면 링크가 깨진다). 결과적으로 시뮬레이터 빌드는 **x86_64 전용**이 되는데,
Xcode 26 은 Rosetta 시뮬레이터를 제거했으므로 애플 실리콘 맥에서는 그 바이너리를
실행할 수 없다. `simctl install` 이 이렇게 답한다:

> ‘Keego’의 업데이트가 필요함 — 해당 앱을 이 iOS 버전에서 사용하려면 개발자가 업데이트해야 합니다.

(전형적인 아키텍처 불일치 메시지다. 앱이 낡아서가 아니다.)

### ⚠️ 그리고 **실기기로도 못 돌린다** — Maestro `test` 가 실기기를 안 잡는다

위 제약을 확인하고 "그럼 실기기로 하면 되겠다"고 갔다가 두 번째 벽을 만났다.
**막다른 길이라는 것 자체가 결론이므로 적어 둔다.**

Maestro 2.8.0 의 iOS 기기 목록에는 **시뮬레이터만** 들어간다:

```
$ maestro list-devices
iOS
  iPhone-17-Pro   iOS-26-5        ← 시뮬레이터
  ...                             ← 연결된 실기기는 없다
```

`maestro test` 는 이 목록을 쓰므로 실기기를 지정해도 거절한다:

```
$ maestro --platform ios --device 00008130-… test .maestro/flows/00-smoke.yaml
Device 00008130-… was requested, but it is not connected.
```

헷갈리는 점: **`maestro hierarchy` 는 실기기를 잡는다**("Detected connected iPhone!" 을
찍고 드라이버까지 빌드한다). 두 명령이 서로 다른 기기 탐색 경로를 쓴다. 그래서
"기기가 붙어 있는데 왜 test 만 안 되지?"로 시간을 버리기 쉽다.

### 정리 — iOS E2E 를 열려면

두 벽이 겹쳐 있고, **하나만 치우면 열린다**:

| 경로 | 막은 것 | 치우는 방법 |
|---|---|---|
| 시뮬레이터 | ML Kit(arm64 시뮬 슬라이스 없음) | **ML Kit → Apple Vision OCR 교체** |
| 실기기 | Maestro `test` 가 실기기 미지원 | Maestro 업스트림 · 또는 Detox(네이티브 러너 필요) · 또는 Maestro Cloud(유료) |

**첫 번째가 현실적이다.** `VNRecognizeTextRequest` 는 온디바이스·의존성 0·한국어 지원이라
CLAUDE.md 의 "먼저 OS/플랫폼이 제공하는 것을 찾는다"에 정확히 해당하고, 덤으로 앱 용량이
약 20MB 줄고 시뮬레이터 개발이 통째로 되살아난다.
**다만 OCR 정확도 재검증이 따라오는 별건이라 여기서는 손대지 않았다.**

그때까지 `.maestro/` 흐름은 **안드로이드에서만** 돈다. 흐름 자체는 플랫폼 중립이라
(`subflows/back.yaml` 이 분기를 흡수한다) 위 둘 중 하나가 풀리는 날 그대로 돌아간다 —
고칠 것이 없다.

### 삼성 오동작 방지 필터
근접센서가 가려지면(폰이 엎어져 있거나 무언가 덮여 있으면) 삼성이 터치를 통째로 막고,
`adb` 로는 풀리지 않는다. 흐름이 전부 "요소를 못 찾음"으로 실패하면 폰부터 확인할 것.
