# 신발 데이터 정본 (shoes-spec)

> keego 신발 카탈로그의 **단일 기준 문서**. 스키마·규칙이 바뀌면 코드보다 먼저 여기를 고친다.
> 제정 2026-07-29.

---

## 0. 왜 이 문서가 필요한가

카탈로그가 두 번 무너졌다.

1. **2026-06-18 이후 갱신이 끊겼다.** 그 사이 나온 인기 모델(ASICS Megablast, Brooks Ghost 18,
   Nike Structure Plus)이 통째로 빠졌고, norda·NNormal·Satisfy 같은 **브랜드 자체가 없었다**.
2. **모델만 넣고 스펙을 안 넣었다.** 그러면 '다음 신발' 비교에서 그 신발은 축이 하나도 안 뜬다
   (쿠션·반발·안정은 카테고리에서 파생돼 같은 카테고리 안에선 전부 같은 값이기 때문).

둘 다 "누가 언제 무엇을 확인했는지"가 데이터에 없어서 생긴 일이다. 그래서 스키마에
`verified`·`searchAliases` 같은 **운영 필드**를 넣고, 검증 스크립트로 갭을 자동 탐지한다.

## 1. 스키마

정본: `types/shoe.ts`

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | ✅ | **슬러그**. 문서 id 이자 영구 키. 예: `hoka-mafate-speed-4-lite-satisfy-stsfy` |
| `brand` | string | ✅ | **실제 제조사**. 콜라보여도 만든 쪽을 적는다(Satisfy×Hoka → `Hoka`) |
| `model` | string | ✅ | 베이스 모델명. 버전 숫자는 뺀다 (`Mafate Speed`) |
| `version` | string \| null | ✅ | 버전. 숫자가 없거나 모델명 자체가 숫자면 `null` (norda `005`) |
| `variant` | string \| null | ✅ | 특별판 표기 (`LITE`, `GTX`, `Wide`). 없으면 `null` |
| `collabWith` | string \| null | ✅ | 협업 상대 (`Satisfy`). 없으면 `null` |
| `category` | Category | ✅ | 아래 §2 |
| `weight` | number \| null | ✅ | 무게(g). **공표된 값 그대로** |
| `weightBasis` | string \| null | ✅ | 그 무게를 잰 사이즈 (`US9`·`US9.5`·`US10`). 모르면 `null` |
| `drop` | number \| null | ✅ | 드롭(mm) |
| `plate` | `'carbon'`\|`'other'`\|`'none'`\|null | ✅ | 미드솔 플레이트. 모르면 `null` |
| `stackHeight` | `{heel, forefoot}` \| null | ✅ | 스택(mm) |
| `releaseYear` | number \| null | ✅ | 출시연도 |
| `defaultLifespanKm` | number | ✅ | §3 — 카테고리 기본값 상속 |
| `discontinued` | boolean | ✅ | 기본 `false` |
| `searchAliases` | string[] | ✅ | 한글표기·오타·축약형. 빈 배열 허용하나 경고 대상 |
| `verified` | boolean | ✅ | 공식 소스로 확인했는가 |

### 규칙

- **필수 = 키가 반드시 있어야 한다.** 값을 모르면 `null`을 넣지 **키를 빼지 않는다**.
  키가 없는 것과 "확인했는데 없음"은 다르고, 후자를 표현할 방법이 있어야 한다.
- **모르면 비운다.** 추측·보간 금지. "비슷한 모델이니 비슷할 것"은 사실이 아니다(Truth only).
- **모델을 넣을 땐 스펙도 같이 넣는다.** 스펙 없는 모델은 비교에서 침묵한다.
- **무게는 환산하지 않는다.** US9.5에서 잰 값을 US9로 고쳐 적는 순간 그건 측정이 아니라
  추정이다. 대신 `weightBasis`에 잰 사이즈를 적는다.
- **`weightBasis` 는 mm 로 통일한다(2026-07-30 확정).** 정본 표기는 `'270mm'` 꼴이고
  표준은 **남성 US9 = 270mm** 다. 변환은 `lib/shoeWeightBasis.ts` 하나만 쓴다.
  · 왜 mm 인가: 소스마다 `US9`·`M9`·`사이즈 9`·`유니섹스 사이즈 9`·`US9(유니섹스)` 로
    적어 두는데, 문자열이 다르다는 이유만으로 **같은 기준인데 비교가 막혔다**(실제로
    34켤레가 그랬다). mm 는 성별·지역 표기에 흔들리지 않는 단일 척도다.
  · 이건 무게 환산이 아니라 **사이즈 이름 통일**이다. 사이즈표의 정의를 쓸 뿐이고
    무게 숫자는 손대지 않는다.
  · 판단 못 하는 표기는 `null`(모름)로 남긴다. **`null` 을 270mm 로 가정하지 않는다.**
- **무게 차이는 기준을 맞춘 뒤에 낸다.** 반 사이즈가 6g 쯤이라 그냥 빼면 안 된다.
  비교 표(`lib/shoeCompareTable.ts`)는 셋으로 나눈다:
    · 기준이 같다 → 그대로 뺀다
    · 기준이 다르고 **둘 다 안다** → 사이즈 보정 후 빼고 `≈` 를 붙인다
    · 하나라도 모른다 → **차이를 안 적는다.** 모르는 걸 보정할 수는 없다
  보정 계수는 **5mm 당 6g**(`GRAMS_PER_5MM`). 같은 모델을 두 사이즈에서 잰 관측쌍
  5건에서 얻었고 범위가 3~9g 이라 **±3g 불확실**하다. 신발끼리 실제 차이가 20~60g 이라
  부호도 크기도 뒤집지 않지만, 추정은 추정이므로 `≈` 로 반드시 밝힌다.
  ⚠ **보정은 화면에서만.** 카탈로그에 저장된 무게는 언제나 공표된 원래 값이고,
  칸에 적히는 숫자도 원래 값이다. 보정은 차이를 낼 때만 쓴다.
- **플레이트는 카테고리로 유추하지 않는다.** tempo 인데 카본인 신발이 흔하고(Zoom Fly 6·
  Mach X 3·Hyperion Max 4), racing 인데 카본이 아닌 신발도 있다(Adizero Adios 9 = 나일론 샹크).
  유리섬유·TPU 플레이트를 `carbon` 으로 적으면 없는 사실을 만드는 것이라 `other` 로 나눈다.
  **'카본 인퓨즈드 나일론'은 `other`다**(Mizuno WAVE PLATE = Rilsan 나일론 + 카본 섬유).
  나일론 베이스를 `carbon` 이라 적으면 카본 플레이트 레이서와 같은 것으로 읽힌다.
  **근거는 제품 설명이어야 한다** — 고객 리뷰에 적힌 플레이트 언급은 쓰지 않는다.
- **`none` 의 근거 기준(2026-07-29 완화).** 처음엔 "없다고 적힌 경우"만 인정했는데, 그러면
  데일리화 대부분이 영원히 `null` 로 남아 이 필드가 무용지물이 된다. 브랜드는 카본
  플레이트를 **절대 숨기지 않는다** — 헤드라인 기능이라 반드시 광고한다. 그래서:
    · `none` = "plate-free" 명시 **또는** 미드솔 구성을 열거한 제품 설명에 플레이트 언급이 없음
    · `null` = 제품 설명 자체를 확인하지 못함
  이건 추측이 아니라 **부재의 증거**다. 다만 근거의 종류가 다르므로 문서에 남긴다.
- **`stackHeight`의 forefoot 은 `heel - drop` 으로 채워도 된다.** 드롭의 정의가 그것이라
  이건 추측이 아니라 산수다. 셋 중 둘을 알면 나머지는 확정된다.

## 2. 카테고리

```
daily | tempo | racing | trail | stability | recovery
```

기존 시드(`data/shoes.json`)는 다른 어휘를 쓴다. **1:1로 대응하므로 매핑으로 잇는다**
(`types/shoe.ts`의 `LEGACY_CATEGORY_MAP`).

| 신규 | 기존 | 비고 |
|---|---|---|
| `daily` | `daily_trainer` | |
| `tempo` | `super_trainer` | 논카본 슈퍼트레이너 |
| `racing` | `carbon_racing` | 카본 레이싱 |
| `trail` | `trail` | |
| `stability` | `stability` | |
| `recovery` | `max_cushion` | ⚠️ 유일하게 의미가 느슨하다 — 맥스쿠션은 '회복주용'이 주 용도라 대응시켰다 |

## 3. 수명(defaultLifespanKm)

**카테고리 기본값을 상속한다.**

| 카테고리 | 기본 수명 |
|---|---|
| `daily` | 650 |
| `tempo` | 650 |
| `racing` | 450 |
| `trail` | 650 |
| `stability` | 700 |
| `recovery` | 700 |

- **variant 는 오버라이드 금지.** `LITE`·`GTX` 같은 파생은 베이스와 같은 수명을 쓴다.
  갑피가 달라도 밑창 수명은 같고, 파생마다 다른 수치를 쓰면 근거 없이 갈린다.
- 모델별 오버라이드는 **공식 근거가 있을 때만** 허용한다(예: 브랜드가 명시).

## 4. 콜라보·특별판

콜라보는 **별도 문서**로 등록한다. 사용자가 그 이름으로 갖고 있고 그 이름으로 찾기 때문이다.

```
id:          hoka-mafate-speed-4-lite-satisfy-stsfy
brand:       Hoka          ← 만든 쪽
model:       Mafate Speed
version:     4
variant:     LITE
collabWith:  Satisfy       ← 이걸로도 검색된다
```

- 스펙은 **베이스와 다를 때만** 따로 적는다. 같으면 베이스 값을 그대로.
- `collabWith`는 검색 대상이다 — "새티스파이"로 찾으면 Hoka·adidas·norda 결과가 같이 나온다.

---

## 5. 단종

**삭제하지 않는다.** `discontinued: true`로만 표시한다.

이유: 사용자가 지금도 그 신발을 신고 있고, 지난 기록이 그 id를 참조한다. 지우면 기록이
고아가 된다. 단종 모델은 '내 신발 등록' 목록에서 뒤로 밀 뿐 사라지지 않는다.

## 6. 검색

매칭 대상(`lib/shoeSearch.ts`):

1. `brand`
2. `model` + `version` + `variant`
3. **`searchAliases`** — 한글표기(`나이키 페가수스`), 오타(`페가서스`), 축약(`페가`)
4. **`collabWith`** — 협업 상대명

### 0건일 때

- `search_misses` 컬렉션에 `{ query, userId, createdAt }` 적재 → **무엇이 없는지 데이터로 안다**
- 화면에 **"내 신발이 없어요"** 버튼 → `shoe_requests`에 `{ brand, model, userId, createdAt }`

이 둘이 §0의 "카탈로그가 낡는 문제"에 대한 구조적 답이다. 사람이 눈치채기를 기다리지 않는다.

---

## 7. 저장 규약

`lib/shoeCatalogRepo.ts`

- **문서 id = 슬러그 고정.** 랜덤 id를 만들지 않는다.
- **`setDoc(..., { merge: true })` upsert 만.** `addDoc` **금지** — 같은 신발이 두 번 생긴다.
- 단종은 `discontinued: true` 필드 갱신으로만. `deleteDoc` 금지.

## 8. 검증

```
npm run validate-shoes
```

- 필수 필드 누락
- `id` 중복
- **같은 라인 version 갭** (39·40·42 → 41 누락 경고). `version: null` 인 라인은 제외
- `searchAliases` 빈 문서 경고
- 브랜드별 등록 수 / 미검증(`verified: false`) 수 요약

## 9. 운영

- 브랜드 커버리지 현황은 `docs/brands.md`에 적는다.
- 기준선은 **편집샵 입점 브랜드**다(굿러너컴퍼니 등) — 실제로 팔리는 것이 곧 사용자가 신는 것.
- 신규 모델 확인 주기: 분기 1회 + `shoe_requests`에 요청이 쌓일 때.

## 10. 소스별 함정 (2026-07-30 추가)

한국 소스를 훑으며 **값을 잘못 읽게 만드는 지점**을 실제로 밟아봤다. 다음에 같은 데를
지나갈 사람이 다시 밟지 않도록 적는다.

### 굿러너컴퍼니 — 스펙 카드는 **상품(성별)별**이다
상세 이미지의 스펙 카드는 모델 스펙이 아니라 **그 상품의** 스펙이다. 여성 상품 페이지의
카드는 여성 무게를 적는다.
- 여성 클라우드몬스터 2 카드 = 245g (남성 정본 295g)
- 여성 클라우드플로우 5 카드 = 231g (남성 정본 272g)

→ **여성 상품 카드에서는 드롭·뒷굽만 취하고 무게는 버린다.** 남성·공용 상품만 무게를 쓴다.
카드가 없는 브랜드도 있다(호카는 마케팅 배너만 있고 스펙 카드가 없다).

### 브룩스 코리아 — 가장 정확하지만 **두 가지 높이**를 구분해야 한다
- 무게에 기준 사이즈가 **명시**된다(남성 270mm). 같은 페이지 사이즈표가 270mm = US 남성 9
  임을 보여주므로 `weightBasis: 'US9'`로 적어도 된다(환산이 아니라 같은 사이즈의 다른 표기).
- **'미드솔 높이'와 'Total Stack Height'는 다른 값이다.** `stackHeight`에는 Total 만 넣는다.
  (고스트 16: 미드솔 24:12, Total 35.5:25.5 — 11mm 차이가 아웃솔·인솔이다.)
- 트레일 카드엔 `PLATE` 행이 있다. `Rock Plate`·`SkyVault v2 Trail Plate`는 카본이라 적혀
  있지 않으므로 `other`, `없음`은 `none`.

### 다나와 — **만장일치일 때만**, 그리고 **무게는 쓰지 않는다**
같은 모델의 상품 코드마다 값이 엇갈린다. 마하 6은 189g이 5:1로 이겼는데 그게 여성용
무게였다 — **다수결은 답이 아니다.** 남성·표준 폭 상품끼리 값이 완전히 일치할 때만 쓴다.
무게는 한 걸음 더 나간다: 다나와는 **기준 사이즈를 밝히지 않는다**(페가수스 42 = 300g,
브랜드 정본 US9 = 292g). 기준을 모르는 무게는 비교를 왜곡하므로 **드롭만** 가져온다.

### 데카트론 코리아 — 구조화된 데이터에 **카본 유무**까지 있다
Kiprun 전용이지만 형태가 가장 좋다. 상세 페이지 데이터에 `"무게 (G)": "243 g"` ·
`"드롭": "6 mm"` · `"카본화": "카본 없음"` 이 들어 있고, 기준 사이즈를 제품별로
명시한다(`"270mm 사이즈 기준 243g"`). 270mm = US 남성 9, 265mm 은 그대로 적는다.

### 웨이백 머신 — 단종 모델은 아카이브에서 되살린다
Running Warehouse 는 지금 전면 404 지만, 아카이브에는 당시 상품 페이지가 그대로 있다.
그리고 그 페이지는 이 카탈로그의 기존 200여 켤레를 채운 **바로 그 원본**이라 출처가
일관된다(리뷰 사이트 같은 2차 전언이 아니다).

  `Shoe Specs (Men's Size 9) Weight 9.6 oz 272 grams`
  `Heel Stack 35 mm  Forefoot Stack 23 mm  Heel-Toe Offset: 12 mm`

효율이 관건이다. 켤레마다 CDX 를 때리면 미스 70%에 6~25초씩 버린다 → **브랜드당 CDX
한 번**으로 아카이브 경로를 전부 받아(19브랜드 2,600여 개) 로컬에서 맞춘 뒤, 실제
있는 것만 재생(replay) 요청한다. 밟은 함정 넷:
  · 404 에 백오프 사다리를 태워 한 켤레에 9분을 버렸다 → 막힘 신호(000/429/503)에만 백오프
  · CDX 는 **오래된 순**으로 준다. 옛 캡처엔 스펙 블록이 아직 없다 → 최신 캡처부터 본다
  · 여성 페이지(SKU `…W2`)의 무게를 모델 무게로 적을 뻔했다 → 여성은 스택·드롭만
  · variant(GTX/WP) 문서는 제외한다 — 그 변형 페이지가 없으면 기본 모델의 무게를 받는다
경로 표기: `Brooks_Ghost_15` · `HOKA_Clifton_8`(대문자) · `ASICS_Gel_Nimbus_25`(밑줄) ·
`Nike_Zoom_Pegasus_39` · `New_Balance_Fresh_Foam_1080_v13`(v 접두, 'X' 는 생략됨).
**adidas 는 RW 가 취급하지 않는다.**

### 값끼리 검산한다 — `npm run validate-shoes`
드롭의 정의가 '뒤꿈치 − 앞발'이라 셋이 서로를 검산한다. 어긋나면 어느 하나가 틀린
것이고, 비교 화면은 그 틀린 값을 그대로 보여준다(사용자는 알 방법이 없다). 그래서
검증 스크립트가 **오류**로 잡는다. 실제로 젤 님버스 27 이 `37/35` 인데 드롭 8 로
저장돼 있었고(아카이브 원본은 `43/35`), 이 검사로 발견해 고쳤다.
무게 120~420g · 드롭 0~15mm · 뒤꿈치 10~65mm 를 벗어나면 경고 — 자릿수를 잘못 읽은
신호다. 다만 **경고가 곧 오류는 아니다**: 미즈노 웨이브 리벨리온 프로 3 은 실제로
뒤꿈치 61mm 다(아카이브로 재확인). 확인 못 하고 물리적으로도 말이 안 되는 값은
**비운다** — 틀린 숫자는 빈칸보다 나쁘다(아디제로 아디오스 프로 에보 3 의 96g).

### Running Warehouse 의 측정 기준 (2026-07-31 확인)
RW 는 **모든 상품 페이지에** 자기 방법론을 적어 둔다. 우리 카탈로그의 400켤레 넘는
값이 이 소스에서 왔으므로 그대로 옮겨 둔다:

> The weight is based on a **Men's size 9** for Men's and Unisex shoes or
> Women's size 8 for Women's shoes. The weight listed is for a **single shoe,
> including the laces.**
> Heel Stack / Forefoot Stack — **Based on Men's size 9 as the standard.**
> Heel-toe Offset — **We use the number given to us by the brand.**

읽히는 것 셋:
  · RW 계열 무게·스택은 전부 **270mm(남성 US9)** 기준이다 — 우리 `weightBasis` 라벨의 근거다
  · RW 무게는 **한 짝 + 신발끈 포함**이다(브랜드 공표값과 몇 g 어긋나는 이유)
  · **드롭만은 브랜드가 준 숫자**를 그대로 쓴다. 그래서 드롭은 RW 든 공홈이든 같아야 하고,
    다르면 둘 중 하나가 잘못 읽힌 것이다(`validate-shoes` 의 검산이 이걸 잡는다)

사이즈 라벨이 없는 신형 페이지도 이 문구가 있으면 기준이 확정된다 — 추론이 아니라
공표된 방법론이다. 문구가 없는 캡처에서는 **비워 둔다.**

### 살로몬 공홈 — 성별·중복·품목을 다 봐야 한다 (2026-07-31 개통)
`salomon.com` 은 Next.js 페이로드에 `Weight per unit` · `Drop Value` · `Heel/Forefoot
Stack Height` 를 그대로 싣는다. 한국 로케일이 없어(국내는 총판) `en-us` 를 쓴다.
한 번에 세 가지를 함께 확인해야 한다 — 셋 다 실제로 틀린 값을 만들 뻔했다:

1. **슬러그가 성별을 구분하지 않는다.** `speedcross-6-lg9212`(남) 와 `-lg9213`(여) 이
   같은 이름이다. 여성 페이지를 물면 스피드크로스 6 이 262g 이 된다(실제 298g).
   → `<title>` 에 `Women` 이 있으면 버린다.
2. **한 페이지에 같은 스펙이 여러 번 나온다**(요약·상세·추천 상품).
   → 값이 갈리면 그 켤레는 통째로 버린다. 조용히 틀린 값보다 빈칸이 낫다.
3. **같은 이름의 옷·가방이 있다.** `S/Lab Pulsar 3` 은 러닝 베스트(90g)다.
   → 신발 전용 필드(`Drop Value`·`Heel Stack Height`·`Lug Depth`)가 하나도 없으면 신발이 아니다.

기준 사이즈는 공표하지 않는다. 대신 **이미 270mm 로 아는 18켤레와 대조해 역산**했다 —
중앙값 차이 0g(범위 −20~+21). 같은 잣대로 본다는 근거가 있어 `270mm` 로 적는다.
재현: `python3 salomon.py calib`.

### 아디다스 — `(사이즈 240mm)` 는 **여성 무게**다 (2026-07-31)
아디다스 글로벌(`adidas.com/us`)이 한국몰과 같은 문구를 영어로 싣는데, 거기서 정체가
드러난다: 여성 페이지는 `Weight: 8.4 ounces (size 7)`, 남성 페이지는 `(size 9)` 다.
**`size 7` = 240mm.** 즉 한국몰의 `중량: 224g(사이즈 240mm)` 도 여성 값이다.

→ 아디다스 무게는 **상품 JSON 의 `"gender":"M"` 을 확인하고**, 기준이 260mm 미만이면
쓰지 않는다. 이 규칙을 안 지켜 `듀라모 스피드 2`(224g)·`프라임 X Evo`(153g)가 남성
스펙 자리에 들어간 적이 있고, 나중에 걷어냈다.

글로벌은 단위도 페이지마다 다르다(`10.3 oz` / `9.7 ounces (size 9)` / `0.39 in`).
**사이즈가 적힌 미터법 페이지**를 우선한다 — 기준 없는 무게는 비교에 못 쓴다.

### 웨이백 CDX — `limit` 이 알파벳 뒤쪽을 통째로 자른다 (2026-07-31)
브랜드당 `limit=5000` 으로 경로를 받았더니 나이키에서 `Zoom_Fly`·`Vaporfly` 가 통째로
없었다. 이미지·색상 URL 이 상한을 먼저 다 먹고 **정렬 뒤쪽(Z…)이 잘린** 것이다.
겉으로는 "아카이브에 없음" 으로 보여서 없는 줄 알기 쉽다.

→ `&filter=original:.*descpage.*` 로 **서버에서 먼저 거르고** 상한을 올린다.
그러자 나이키 경로가 397 → 607 개가 됐다. 다른 브랜드는 상한에 안 걸려 그대로였다.

### 아카이브에서 캡처를 고르는 법 (2026-08-01)
같은 URL 이라도 캡처마다 내용이 다르다. 세 가지를 안 지키면 있는 데이터를 놓친다.

1. **상품코드 URL 을 버리지 마라.** 스펙이 있는 건 `.../ultraboost-22-shoes/GX5462.html`
   쪽이다. 경로가 슬러그로 *끝나는지*(`endswith`)만 봤더니 그게 전부 빠지고, 스펙 없는
   목록 URL 만 남았다. 경로 **안에** 슬러그가 있으면 받는다.
2. **최신 캡처부터 보지 마라.** 상품이 내려간 뒤의 캡처는 4KB 짜리 리다이렉트 껍데기다.
   쿼리 없는 URL 을 먼저, **오래된 캡처**(상품이 살아 있던 때)를 먼저 본다.
   본문이 200KB 미만이면 껍데기로 보고 다음 캡처로 넘어간다.
3. **재생이 실패하는 스냅샷이 흔하다.** 캡처 자체가 406/오류 페이지인 경우가 있다
   (미즈노 웨이브 라이더 27 은 스냅샷이 하나뿐인데 그게 406 이다 — 복구 불가).
   그래서 한 켤레에 캡처를 여러 개 넘겨 봐야 한다.

### 옛 아디다스 페이지 — 그램 + UK 사이즈 (2026-08-01)
2021~22 년 adidas.com 은 이렇게 적었다: `Weight: 333 g (size UK 8.5)`.
**이 표기 자체가 성별 근거다** — 남성은 UK 8.5(275mm), 여성은 UK 5.5 로 잰다
(한국몰 i18n 라벨 `features.runningIcons.sizeWeightMen/Woman` 으로 확인).
그래서 옛 페이지엔 `"gender"` 필드가 없어도 기준 사이즈로 성별을 가를 수 있다.

스택 표기도 다르다: `(heel: 39.5 mm / forefoot: 31 mm)` — **콜론이 붙는다.**
콜론을 안 받아 주는 정규식이 스택을 통째로 버리고 드롭만 건지고 있었다.

### 유령 항목 — 없는 신발은 지운다 (2026-08-01)
울트라부스트 23·24·25 가 카탈로그에 있었는데 **제품으로 나온 적이 없다.**
아디다스 라인업은 19 → 19.5 → 20 → 21 → 22 → 라이트 → 5 → 5X 다.
옛 351켤레 이관 때 버전 번호를 기계적으로 이어 붙인 흔적이었다(셋 다 `releaseYear` 없음).

판정 기준은 **"비어 있다"가 아니라 "버전 번호가 조작됐다"** 이다. 스펙이 네 항목 다 빈
문서가 98개나 되지만 대부분 실존 모델이다(윈플로 9·10·11, 젤 벤처 9, 카와나 2·3 …).
지우기 전에 이 셋을 확인한다:
 · 브랜드 아카이브 캡처에 그 슬러그가 하나도 없는가
 · 현행 사이트맵(글로벌·국내) 어디에도 없는가
 · `releaseYear` 가 비어 있고, 같은 라인의 실존 모델은 차 있는가

**404 만으로 판정하지 마라.** On 은 실제 URL 이 상품코드를 포함해서, 슬러그만으로 찍은
404 는 실존 모델(클라우드서퍼 2)에도 똑같이 난다. 그 방법으로는 아무것도 증명 못 한다.

지워도 **사용자 기록은 안 깨진다** — 등록한 신발은 카탈로그 id 가 아니라 brand/model
문자열로 저장되고, `lib/shoeCatalogLookup` 은 못 찾으면 null 을 준다(직접 입력한 신발과
같은 취급). 다만 **Firestore 에 이미 올렸다면 원격 문서는 남는다** — seed 스크립트에
삭제 경로가 없다(단종은 삭제가 아니라 플래그로 다루는 설계).
