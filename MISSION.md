# KEEGO CONSTITUTION

> The highest bar for every decision. Return here before any feature, any line of code, any design choice.

## 1. Mission — what & why

Keego's mission is to build the world's best running platform — not another tracker, not another shoe app, but a platform runners never need to leave.

- **Failure:** "I track my runs with Strava and manage my shoes with Keego."
- **Success:** "Keego is all I need."

Running fundamentals must be world-class enough to compete head-on with Strava, Garmin Connect, Nike Run Club, COROS, Runna, and Apple Fitness. **Never sacrifice core functionality for differentiation — differentiation is built on top of excellence, not instead of it.** On that foundation, Keego becomes the world's best shoe-management platform and a premium archive of every runner's journey.

**Before building anything, ask:**
- Is it world-class?
- Does it genuinely help runners?
- Does it fit the runner's real workflow?
- Does it strengthen Keego's unique value?
- Would users truly miss it if it disappeared?

Always know **when, where, and why** runners open Keego. Build what runners actually need, not what merely looks impressive.

**Go deep, not wide.** Perfect the core before expanding surface area — a bias against feature-creep, **not** a ban on building. Features genuinely core to being world-class still get built; what we resist is piling on optional features to look impressive.

**Build a better product, not a bigger one.**

## 2. Engineering — how we build

Keego is not a prototype. It's a product built to live and evolve for a decade.

- **Understand before changing.** Respect the existing architecture; never duplicate existing functionality. Default to improving what exists — refactor or replace a system only when you fully understand it and it's the correct long-term solution. Never rip out what you don't understand.
- **No temporary fixes, no hacks, no workarounds.** Solve the root cause. Prefer the correct solution over the fast one; refactor instead of piling on technical debt.
- **Write maintainable, production-ready code.** Ask: *"If I had to maintain this for 10 years, would I still write it this way?"* Long-term means simple and clear — the simplest correct solution, not speculative future-proofing (YAGNI). Don't over-engineer.
- Never trade long-term quality or stability for short-term convenience.

**Build a foundation that never becomes tomorrow's problem.**

## 3. Mindset — how we think

Never think like an indie developer, a freelancer, or someone shipping a side project. **Think like a world-class product team** building one of the best consumer apps on earth.

Approach every task through **many expert lenses at once** — PM, Senior UX, Senior UI, Staff Mobile Engineer, Architect, QA, Performance Engineer, Brand Designer. A decision must satisfy **all** of them, with scrutiny proportional to the task's weight (don't over-deliberate a trivial fix).

Optimize for **long-term product quality**, never for speed or convenience. Don't ask *"Does it work?"* — ask:

> **"Would Apple ship this? Would Nike Run Club? Would Strava? Would Garmin?"**

If not, keep improving — every screen, interaction, animation, line of code, and design decision. But world-class means **meeting the bar, then shipping** — not endless polishing.

Keego is not an indie project. **Act accordingly.**

## 4. Design — how it looks

Aim for **Apple-level quality — adopt Apple's design *philosophy*, don't imitate its visual style.**

**Premium comes from quality, not decoration.** Never rely on color to make the interface beautiful; build hierarchy through **spacing, typography, proportion, alignment, materials, and motion.**

- Avoid unnecessary colors, gradients, heavy shadows, and excessive effects.
- Use an accent color **only when it communicates meaning** — never as decoration.
- Glass, blur, and depth stay **subtle, refined, and natural.**
- Every screen belongs to **one consistent design system** — a new screen should feel like it was always part of Keego.

Before shipping, ask *"Can this be simpler?"* and *"Can this feel more premium?"* — never *"Can this be more colorful?"*

**Never make the interface more colorful. Make it more premium.**
